# REVIEW.md（push 前レビューの注意点）

このファイルは、main へ直接 push する前のレビューでレビュー役が注意すべき点を集めたものです。
kuma-agent には PR と CI の関門が無いため、この push 前レビューが唯一のレビュー関門です。

## 使い方

- レビュー役は、実装したセッションとは別のセッションが務める（`AGENTS.md` の「push 前レビュー」節）。
- 読むのは**直前のコミット済み版**のこのファイルです。レビュー対象の変更に含まれる版は読まない
  （変更が自分の物差しを変えられないようにするため）。
- 指摘は **Important（直すべき）／ Nit（任意）／ Pre-existing（既存の問題で、この変更の責任ではない）**
  のいずれかを付けて返す。Pre-existing はその場で直させず、このファイル末尾の候補欄か Issue 相当の記録へ回す。

## 注意点

### 範囲と進め方（レーン相当の注意）

- 依頼された範囲の外のファイル・振る舞いを変えていないか。頼んでいない変更（drive-by）が混ざっていたら Important。
- 依存は最小限（httpx のみ）を保つ。新規依存の追加は、所有者の判断なしに入っていないか。
- 開発専用のテスト依存（Hypothesis 等）は入れない方針（2026-11-21 所有者承認）。往復変換・同等性の
  検証は、標準の parametrize 等で手書きする。

### 秘密情報

- API キー・トークンは環境変数からのみ読む。コード、テスト、ログ、完了報告、コミットメッセージの
  いずれにも値そのものが出ていないか。
- `.env` 実ファイルや秘密情報を含むファイルが変更対象に含まれていないか。

### 利用者向けの文言と画面

- 利用者向け文言に内部用語を使わない。画面表示のモード名は「相棒モード」「スレッドモード」に統一し、
  内部の仕組みを指す言葉（例: 台帳）を利用者向け文言に出さない。
- Web UI または TUI の見た目・操作が変わる変更では、README の画面資産
  （`assets/screenshot-web.png` / `assets/screenshot-tui.png` / `assets/demo-web.gif` / `assets/demo-tui.gif`、
  テーマ別ギャラリーの静止画と 8 ビット動画を含む）を実画面で撮り直して差し替えているか。
  差し替えが無い UI 変更は、理由が完了報告に書かれていない限り Important。
- 画面資産の会話の中身は、実データではなくスタブモデルの応答に差し替えているか。

### 振る舞いとデータの安全

- 記憶・書き出し・控え（export / restore）・テナント分離に触れる変更では、分離漏れ
  （他テナントや他利用者のデータが混ざる・漏れる）が無いか特に見る。
- データを消す・上書きする変更は、対象の限定と取り消し可能性を確認する。不可逆な変更は Important として扱う。
- 型注釈を付け、`from __future__ import annotations` を使う作法が守られているか。

### 検証の記録

- コミット末尾のトレーラー（`Agent:` / `Agent-Env:` / `Verified:`）が付いているか。
  `Verified:` の値は `docs/VERIFY.md` の定義に従う。
- `docs/VERIFY.md` のチェック（pytest 全量、UI 変更時の実画面確認、振る舞いに触れる変更の実動記録）が
  完了報告に残っているか。

## 見逃し→ルール化の候補欄

push 後の手直しが必要になった見逃しや、本番（所有者の利用）で問題が出た見逃しは、ここに記録して貯めます。

- 候補の条件: 同種の見逃しが **2回以上** 現れた、または差分から識別できる（発火条件を差分の特徴で書ける）もの。
  ただしデータ損失・秘密情報の漏れのような重大なものは1回でも候補にする。
- 候補になったら、別のセッションに「このルールが誤検知する変更」を探させ（反証）、残ったものだけを
  上の「注意点」へ追記する。追記の承認は通常の変更と同じ手順（レビュー＋検証）で行う。
- 使われなくなった・重複した注意点は、月1回程度の棚卸しで削る。
