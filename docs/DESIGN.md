# kuma-agent 設計メモ

## 目的

Muse（Meta の個人エージェント）のような「対話型の相棒エージェント」を
自作する。単発のタスク自動化ではなく、同じ相手と長く付き合い、人格と
記憶を持ち、道具で現実の作業もできる存在を目指す。

当初の構想（GitHub Issue を拾う自律開発エージェント）から方針転換した
（2026-11-01）。開発タスクの自動化は将来の「道具」の 1 つとして扱う。

## 構成

```
src/kuma_agent/
  cli.py       エントリポイント（chat）
  config.py    設定（モデル、データ置き場、API キー）
  llm.py       LLM バックエンド（API 系 3 種）と共通の Message 表現
  agent_cli.py エージェント実行環境（CLI 系 2 種）をバックエンドにする実装
  persona.py   人格ファイル（SOUL.md / IDENTITY.md / USER.md）の読み込み
  memory.py    長期記憶（MEMORY.md）と会話履歴の読み書き・検索
  tools.py     道具の登録と実行（ファイル、シェル、時刻など）
  tasks.py     用事の台帳（ユーザーごとに tasks.json へ保存）
  session.py   1 回の対話セッション（履歴管理、道具呼び出しの循環）
data/（実行時に作る、リポジトリには入れない）
  SOUL.md / IDENTITY.md / USER.md / MEMORY.md / conversations/
  tasks.json（ユーザーの台帳）
  tenants/<テナント名>/ … 既定以外のテナントのデータ（同じ構成を繰り返す）
  users/<ユーザー名>/ … テナントごとの置き場の中に置く、既定以外の
    ユーザーのデータ（同じ構成を繰り返す）
```

## 対話ループ

1. 人格ファイルと長期記憶を読み、システムプロンプトを組み立てる
2. 利用者の発話を受ける
3. LLM が応答する。道具の呼び出しがあれば実行して結果を戻し、
   呼び出しがなくなるまで循環する
4. 会話履歴を保存する。重要な事実は長期記憶へ書き出す（要約と抽出）

## 記憶の設計

- **長期記憶**（MEMORY.md）: 人間が読める Markdown。事実・好み・約束を
  箇条書きで保持し、毎回の対話の冒頭で読み込む
- **会話履歴**: セッションごとの JSONL。検索は当面は単純なキーワード一致
- 書き込みはエージェント自身が行い、利用者がいつでも直接編集できる

## テナント方式

データの区切りの一番外側に「テナント」を置く。区切りの階層は
**テナント ＞ ユーザー ＞ 台帳** で、部屋（セッション）は
スレッドモードのときにユーザーの内側で会話を分ける。テナントが違えば、
その下のユーザー・人格ファイル・長期記憶・部屋・台帳のすべてが
別物になる。

- **実効データ置き場**: テナントごとに、データの置き場そのものを
  分ける。既定テナント（名前は `default`）は後方互換のため従来の
  `data/` をそのまま使い、それ以外のテナントは
  `data/tenants/<テナント名>/` を使う。テナント名はセッション ID と
  同じ正規化（ファイル名に安全な形）を通す。
- **指定方法**: 環境変数 `KUMA_TENANT`、または CLI の
  `chat --tenant <名前>` / `web --tenant <名前>`（CLI 引数が優先）。
  テナントの実効データ置き場は `Config.tenant_data_dir` が返す。
  その内側でさらにユーザーの置き場（次節）が分かれる。
- **Web UI**: サーバーはテナントごとに UserStore を持ち、ページの
  ヘッダーでテナントの切り替え・新規作成ができる。テナントを切り替える
  と、そのテナントのユーザー一覧・部屋一覧と履歴に切り替わる
  （`GET /api/tenants`、各リクエストの `tenant` 指定）。
- **対象外**: CLI 系バックエンドが添付を保存する
  `.kuma-attachments/`（作業ディレクトリ配下）は、作業対象の
  ファイルの一部として扱い、テナントでは分けない。相手のエージェントが
  作業ディレクトリで読める必要があるため。

## ユーザー

テナントの下に「ユーザー」を置く。ユーザーは分離の単位であり、
同じテナントでもユーザーごとに人格ファイル・長期記憶・部屋・台帳が
すべて分かれ、互いに混ざらない。家族で 1 つのテナントを共有する
ような場合に、相手ごとに文脈を分けるための区切りである。

- **実効データ置き場**: 既定ユーザー（名前は `default`）は後方互換の
  ためテナントの置き場をそのまま使い、それ以外のユーザーは
  `<テナント置き場>/users/<ユーザー名>/` を使う。ユーザー名は
  テナント名と同じ正規化（ファイル名に安全な形）を通す。実効データ
  置き場は `Config.user_data_dir` が返し、Session は Persona /
  Memory / TaskBoard のすべてをこの置き場で構築するので、ユーザーを
  またいで情報が漏れる経路はない。
- **識別は宣言であり、認証ではない**: ユーザーの識別は、環境変数
  `KUMA_USER`、CLI の `chat --user <名前>` / `web --user <名前>`
  （CLI 引数が優先）、Web 画面での選択、といった「宣言」によるもの
  で、パスワード等の照合は行わない。なりすましを防ぐ仕組みでは
  ないので、信頼できる範囲（単一マシン・ローカル利用）での分離と
  位置づける。
- **ユーザー管理をしない場合**: 何も指定しなければ既定ユーザーのまま
  単一ユーザーで動く。データの置き場も従来のレイアウトそのままで、
  従来の運用と何も変わらない。ユーザーを分けたくなったときだけ
  名前を指定すればよい。
- **Web UI**: サーバーはテナントごとに、さらにユーザーごとに
  SessionStore を持ち、ページのヘッダーでユーザーの切り替え・
  新規作成ができる。ユーザーを切り替えると、そのユーザーの部屋一覧と
  履歴に切り替わる（`GET /api/users` は `?tenant=` で対象テナントを
  指定し、そのテナントのユーザー一覧と起動時ユーザーを返す。各
  リクエストの `user` 指定でも切り替えられる）。

## セッション管理

会話の文脈の管理は、モード（後述）で選んだどちらか一方の方式で
行う。話題そのものが別ならスレッドモードで会話を分け、1 つの
会話の中で用事が入れ替わるなら寄り添いモードで用事ごとの状態を
分ける。どちらもテナントとユーザーの内側の区切りであり、テナントや
ユーザーを越えては共有しない。

1. **部屋（名前付きセッション、スレッドモードで使う）**: 会話は
   名前付きのセッションに分かれる。記録は
   `conversations/<session_id>.jsonl` に分かれ（ID はファイル名に
   安全な形へ正規化される）、再開時はそのセッションの過去の発話
   だけを履歴へ復元する。CLI は `chat --session <名前>`（既定は
   `main`）、Web UI はヘッダーのセレクトで切り替え・新規作成
   できる。添付ファイルの実体は復元せず、記録に残る要約文だけが
   文脈に戻る。
2. **台帳（用事の管理、寄り添いモードで使う）**: 用事が切り替わる
   たびに台帳へ用事を登録し、用事ごとに題名・状態（open / done）・
   最新のメモを持たせる。台帳は用事の持ち主である**ユーザーごとに
   1 冊**だけを持ち、ファイルはユーザー置き場直下の `tasks.json` に
   置く（階層は テナント ＞ ユーザー ＞ 台帳）。エージェントは道具
   （`list_tasks` / `create_task` / `update_task`）で台帳を読み書き
   する。`list_tasks` は台帳にある用事を状態付きですべて返し、
   `update_task` は ID で更新できる。対話の開始時は進行中の用事を
   すべてシステムプロンプトへ注入する。
   旧仕様の部屋ごと台帳（`tasks/<部屋名>.json`）が残っている場合は、
   台帳の読み込み時にそのまま本体へ取り込む。ID が衝突したら
   使われていない番号へ振り直し、取り込みが済んだ旧ファイルは
   削除する。旧データの用事に残っている余分なキー（かつての
   `room` など）は無視して読み込む。
3. **要約による圧縮（コンパクション）**: 履歴の発話数（user/assistant）が
   閾値を超えたら、古い発話をモデル自身に要約させ、
   「（これまでの会話の要約）」の 1 発話に置き換えて会話を続ける。
   閾値は環境変数 `KUMA_COMPACT_AFTER_MESSAGES`（既定 40、0 で無効）、
   残す直近の発話数は `compact_keep`（既定 10、`KUMA_COMPACT_KEEP_MESSAGES`
   でも変更可）。要約は記録にも `summary` として残り、再開時は
   「要約レコード以前の発話は圧縮済み」として復元される。要約に失敗
   したらその回は圧縮を諦め、履歴はそのまま保つ。要約は履歴を渡す前に
   行うので、API 系・CLI 系どちらのバックエンドでも同じ仕組みが働く。
4. **長期記憶（MEMORY.md）**: セッションを越えて残すべき事実はこちらに
   分ける。セッションの履歴は「部屋ごとの文脈」、長期記憶は「部屋を
   越えた事実」という役割分担にする。

## モード（会話の進め方の選択）

会話をどう進めるかは、モードとして 2 つから選べる。設定は環境変数
`KUMA_MODE` または CLI の `--mode`（`chat` / `web`、環境変数より
優先）で、値の識別子は英語のまま、画面や文面では表示名で出す
（表示名への対応付けは `config.MODE_LABELS` に集約する）。既定は
寄り添いモード。不正な値は既定に倒し、旧値 `both` は後方互換の
ため寄り添いモード（`ledger`）として扱う。

- **寄り添いモード**（`ledger`、既定）: 会話はひとつ。抱えている
  用事を覚えていて、一緒に進めます。部屋は 1 つ（`main`）に固定し、
  話題ごとの用事をユーザーごとに 1 冊の台帳で分けて管理する。
  セッション ID の指定は無視される。進行中の用事はすべて注入する。
  このモードでは「部屋」は実質存在しないので、Web UI では部屋の
  選択・作成 UI 自体を表示しない（ページは起動時メタ情報
  `GET /api/meta` でモードと表示名を知り、ヘッダーに表示名を出す）。
- **スレッドモード**（`wall`）: 会話をスレッドごとに分けて、
  それぞれ独立に進めます。台帳は使わず、話題は部屋の切り替え
  だけで分ける。台帳系の道具は登録されず、進行中の用事の注入も
  行わない。スレッドは作成・選択・削除ができる。Web UI では
  画面上部の UI（このモードでは呼称が「部屋」から「スレッド」に
  切り替わる）から作成・選択・削除を行い、削除は
  `POST /api/sessions/delete` で記録ファイルを消してサーバー側の
  Session も破棄する。運用者は CLI の `kuma-agent threads`
  （一覧表示と `--delete`、`--tenant` / `--user` で対象を指定）
  でも扱える。削除の対象は `memory.delete_session_record` が
  一手に担い、消すのはそのスレッドの記録ファイルだけで、台帳や
  長期記憶には触れない。`main` も削除でき、その場合は次に開いた
  ときに空の記録で再開する。

CLI / TUI では、寄り添いモードで `--session` に別の部屋が
指定されていても起動時に「部屋は main に固定されます」と 1 行
知らせる。

## 保管と保持期限

kuma-agent は将来、コンテナでサービスとして動かす想定である。その
場合、利用者はデータ置き場のファイルを自分で消すことができない。
「消すまで残る」では置き場が際限なく膨らんでしまうため、記録には
保持期限を設け、期限を過ぎたものはシステム側が自動で掃除する。

- **設定**: 保持期限は環境変数 `KUMA_RETENTION_DAYS`（既定 **90 日**、
  `Config.retention_days`）。**0 で無期限**となり、従来どおり何も
  消さない。
- **テナントごとの保持期間**: 保持期間はテナントごとに変えられる。
  データ置き場ルートの設定ファイル `retention.json` に
  `{"tenants": {"<テナント名>": <日数>}}` と書くと、そのテナント
  だけ指定の日数になる（0 でそのテナントだけ無期限）。ここに無い
  テナントは全体の既定を使う。負数や数値でない値の項目は無視して
  全体既定に倒し、ファイルが無い・壊れている場合も例外にせず
  全体の既定で動く。
- **優先順位**: 保持期間の決定は **`--days` ＞ `retention.json` ＞
  全体の既定** の順。`kuma-agent cleanup --days <日数>` はその場
  限りの上書きで、対象範囲すべてにその日数を適用する。
- **対象**: 全テナント×ユーザー置き場を走査し（`memory.cleanup_expired`）、
  次だけを掃除する。
  - 部屋の記録ファイル（`conversations/*.jsonl`）のうち、最終更新が
    期限より古いものをファイルごと削除する。
  - 台帳（全台帳ファイル: `tasks.json` と `tasks/*.json`）のうち、
    完了（done）してから更新が期限より古い用事だけを取り除く。
    ファイル自体と進行中の用事は残す。
  - 長期記憶（MEMORY.md）と人格ファイルは対象外で、消さない。
- **実行タイミング**: Web サーバーの起動時に 1 回自動で実行する。
  運用者は `kuma-agent cleanup` でもいつでも実行でき、
  `--dry-run` を付けると削除せずに対象の件数だけを確認できる。
  `--tenant <名前>` を付けるとそのテナントの置き場（配下の全
  ユーザー）だけを対象にでき、他のテナントには触れない。実行時は
  対象テナントと適用した保持期間を表示する。Web 起動時の自動掃除
  でも `retention.json` の指定は自然に効く。
- **壊れたデータへの態度**: 置き場が無い・読めないファイルがある等
  では落とさず、その分を飛ばして掃除を続ける。

## 作業中表示（UI）

LLM の応答や道具の実行には時間がかかることがあるため、UI には
「今なにをしているか」をアニメーション付きで出す。頭文字のような
記号表示ではなく、実際の作業に応じた文言にする。

- **中核（Session）**: `Session.on_status` コールバックが対話ループの
  各段階で現在の作業を通知する。モデルへの問い合わせ開始時は
  「考え中」、道具の実行直前は道具ごとの作業名（`tools.activity_label`:
  例えば read_file は「ファイルを読んでいます」で、ファイル名など
  安全な手がかりがあれば添える）、要約圧縮の実行時は「会話を要約中」。
  応答が終わったら空文字列を通知して表示なしに戻す。CLI 系
  バックエンドでも問い合わせは同じ経路を通るので同じ表示が出る。
- **Web UI**: サーバー側で部屋ごとの現在の状態を保持し、
  `GET /api/status`（tenant / user / session の指定に対応）で返す。
  ページは送信中ポーリングで状態を取り、入力欄の上に「うごめく点＋
  状態文言」の行を表示し、応答が返ったら消す。
- **TUI**: 応答待ちの間は `Session.say` を別スレッドで実行し、入力欄の
  上の行に状態文言とフレームごとに変わる点を出し続ける。待ち中も
  ログのスクロール（PageUp / PageDown）と終了は受け付ける。
- **プレーンな CLI**: 状態をキャリッジリターンで同じ行に上書き表示し、
  応答前に行を消す簡易表示。

## 人格の設計

- SOUL.md: 振る舞いと価値観（口調、姿勢、好み）
- IDENTITY.md: 名前・呼び名・シグネチャ
- USER.md: 相手（利用者）の情報。名前、タイムゾーン、関心事
- 人格はコードから分離し、ファイルの差し替えで別キャラクターにできる

## 道具（ツール）

最初に用意するもの:
- ファイルの読み書き（作業ディレクトリ内）
- シェルコマンドの実行（確認が必要な操作は利用者に聞く）
- 現在時刻・日付の取得
- 記憶の検索と書き込み

将来: Web 検索、カレンダー、GitHub（Issue 駆動の開発補助を含む）

## 安全装置

- 取り返しのつかない操作（削除、送信、公開）は利用者の確認を取る
- API キーは環境変数からのみ読む（`META_MODEL_API_KEY`）
- 道具の実行範囲は作業ディレクトリと許可リストに制限する

## LLM バックエンド（決定済み）

頭脳は差し替え可能にし、5 種を用意する。選択は環境変数
`KUMA_LLM_PROVIDER`（既定 muse）、モデルは `KUMA_LLM_MODEL`。

API 系（kuma-agent が道具ループを回す）:
- `muse`: Meta Model API（Muse Wonder）。キー: META_MODEL_API_KEY
- `claude`: Anthropic Messages API。キー: ANTHROPIC_API_KEY
- `gemini`: Google Gemini API。キー: GEMINI_API_KEY

CLI 系（相手側が道具ループを持つ。文脈をプロンプトで渡し、作業
ディレクトリでヘッドレス実行する。認証は各 CLI のログインを使う）:
- `claude-code`: Claude Code CLI（`claude -p`）
- `gemini-cli`: Gemini CLI（`gemini -p`）
- `codex`: OpenAI Codex CLI（`codex exec`、workspace-write サンドボックス）

既定モデルは 2026-11 時点の最新に合わせている（Claude Sonnet 5.5 /
Opus 5.5、Gemini 3.8 Flash / 4 Argon）。モデルは移り変わりが速いので、
既定値は定期的に見直す前提で各クライアントに明記する。

## Meta Model API の使い方

- OpenAI 互換の Chat Completions 形式（`https://api.meta.ai/v1`、
  モデル `muse-wonder-1.0`、Bearer 認証）
- 人格などの誘導は `developer` ロールで渡す
- 関数ツールは OpenAI 形式。`stop`・`logit_bias`・
  `reasoning_effort="none"` は送らない（400 になる）
