# kuma-agent 設計メモ

## 目的

Muse（Meta の個人エージェント）のような「対話型の相棒エージェント」を
自作する。単発のタスク自動化ではなく、同じ相手と長く付き合い、人格と
記憶を持ち、道具で現実の作業もできる存在を目指す。

当初の構想（GitHub Issue を拾う自律開発エージェント）から方針転換した
（2026-11-01）。開発タスクの自動化は将来の「道具」の 1 つとして扱う。

## 構成

```
src/kuma_agent/
  cli.py       エントリポイント（chat）
  config.py    設定（モデル、データ置き場、API キー）
  llm.py       LLM バックエンド（API 系 3 種）と共通の Message 表現
  agent_cli.py エージェント実行環境（CLI 系 2 種）をバックエンドにする実装
  persona.py   人格ファイル（SOUL.md / IDENTITY.md / USER.md）の読み込み
  memory.py    長期記憶（MEMORY.md）と会話履歴の読み書き・検索
  memory_tidy.py 長期記憶の整理（機械的な重複除去とモデルによる統合）
  memory_extract.py 長期記憶の自動抽出（新しい会話からモデルが抽出）
  tools.py     道具の登録と実行（ファイル、シェル、時刻など）
  tasks.py     用事の一覧（ユーザーごとに tasks.json へ保存）
  settings.py  テナントごとの設定（settings.json、能動発信の ON/OFF）
  proactive.py 能動発信（定期チェックと main の会話への投稿）
  jobs.py      定期ジョブ（ユーザーごとに jobs.json へ保存、巡回で実行）
  outputs.py   成果物（ユーザーごとの outputs/ と index.json）
  telegram.py  Telegram 接続（Bot API のロングポーリングで会話する）
  line_api.py  LINE 接続（Messaging API の Webhook で受け、Reply / Push で返す）
  notify_prefs.py 知らせる・知らせないの好み（notify_prefs.json）
  session.py   1 回の対話セッション（履歴管理、道具呼び出しの循環）
data/（実行時に作る、リポジトリには入れない）
  SOUL.md / IDENTITY.md / USER.md / MEMORY.md / conversations/
  tasks.json（ユーザーの用事の一覧）
  tenants/<テナント名>/ … 既定以外のテナントのデータ（同じ構成を繰り返す）
  users/<ユーザー名>/ … テナントごとの置き場の中に置く、既定以外の
    ユーザーのデータ（同じ構成を繰り返す）
```

## 対話ループ

1. 人格ファイルと長期記憶を読み、システムプロンプトを組み立てる
2. 利用者の発話を受ける
3. LLM が応答する。道具の呼び出しがあれば実行して結果を戻し、
   呼び出しがなくなるまで循環する
4. 会話履歴を保存する。重要な事実は長期記憶へ書き出す（要約と抽出）

## 記憶の設計

- **長期記憶**（MEMORY.md）: 人間が読める Markdown。事実・好み・約束を
  箇条書きで保持し、毎回の対話の冒頭で読み込む
- **会話履歴**: セッションごとの JSONL。検索は当面は単純なキーワード一致
- 書き込みはエージェント自身が行い、利用者がいつでも直接編集できる
- 長期記憶が大きくなった場合の検索と注入の切り替えは
  「長期記憶の検索」節に書く

## テナント方式

データの区切りの一番外側に「テナント」を置く。区切りの階層は
**テナント ＞ ユーザー ＞ 用事の一覧（tasks.json）** で、部屋（セッション）は
スレッドモードのときにユーザーの内側で会話を分ける。テナントが違えば、
その下のユーザー・人格ファイル・長期記憶・部屋・用事の記録のすべてが
別物になる。

- **実効データ置き場**: テナントごとに、データの置き場そのものを
  分ける。既定テナント（名前は `default`）は後方互換のため従来の
  `data/` をそのまま使い、それ以外のテナントは
  `data/tenants/<テナント名>/` を使う。テナント名はセッション ID と
  同じ正規化（ファイル名に安全な形）を通す。
- **指定方法**: 環境変数 `KUMA_TENANT`、または CLI の
  `chat --tenant <名前>` / `web --tenant <名前>`（CLI 引数が優先）。
  テナントの実効データ置き場は `Config.tenant_data_dir` が返す。
  その内側でさらにユーザーの置き場（次節）が分かれる。
- **Web UI**: サーバーはテナントごとに UserStore を持ち、ページの
  ヘッダーでテナントの切り替え・新規作成ができる。テナントを切り替える
  と、そのテナントのユーザー一覧・部屋一覧と履歴に切り替わる
  （`GET /api/tenants`、各リクエストの `tenant` 指定）。
- **対象外**: CLI 系バックエンドが添付を保存する
  `.kuma-attachments/`（作業ディレクトリ配下）は、作業対象の
  ファイルの一部として扱い、テナントでは分けない。相手のエージェントが
  作業ディレクトリで読める必要があるため。

## ユーザー

テナントの下に「ユーザー」を置く。ユーザーは分離の単位であり、
同じテナントでもユーザーごとに人格ファイル・長期記憶・部屋・用事の記録が
すべて分かれ、互いに混ざらない。家族で 1 つのテナントを共有する
ような場合に、相手ごとに文脈を分けるための区切りである。

- **実効データ置き場**: 既定ユーザー（名前は `default`）は後方互換の
  ためテナントの置き場をそのまま使い、それ以外のユーザーは
  `<テナント置き場>/users/<ユーザー名>/` を使う。ユーザー名は
  テナント名と同じ正規化（ファイル名に安全な形）を通す。実効データ
  置き場は `Config.user_data_dir` が返し、Session は Persona /
  Memory / TaskBoard のすべてをこの置き場で構築するので、ユーザーを
  またいで情報が漏れる経路はない。
- **識別は宣言であり、認証ではない**: ユーザーの識別は、環境変数
  `KUMA_USER`、CLI の `chat --user <名前>` / `web --user <名前>`
  （CLI 引数が優先）、Web 画面での選択、といった「宣言」によるもの
  で、パスワード等の照合は行わない。なりすましを防ぐ仕組みでは
  ないので、信頼できる範囲（単一マシン・ローカル利用）での分離と
  位置づける。
- **ユーザー管理をしない場合**: 何も指定しなければ既定ユーザーのまま
  単一ユーザーで動く。データの置き場も従来のレイアウトそのままで、
  従来の運用と何も変わらない。ユーザーを分けたくなったときだけ
  名前を指定すればよい。
- **Web UI**: サーバーはテナントごとに、さらにユーザーごとに
  SessionStore を持ち、ページのヘッダーでユーザーの切り替え・
  新規作成ができる。ユーザーを切り替えると、そのユーザーの部屋一覧と
  履歴に切り替わる（`GET /api/users` は `?tenant=` で対象テナントを
  指定し、そのテナントのユーザー一覧と起動時ユーザーを返す。各
  リクエストの `user` 指定でも切り替えられる）。

## セッション管理

会話の文脈の管理は、モード（後述）で選んだどちらか一方の方式で
行う。話題そのものが別ならスレッドモードで会話を分け、1 つの
会話の中で用事が入れ替わるなら相棒モードで用事ごとの状態を
分ける。どちらもテナントとユーザーの内側の区切りであり、テナントや
ユーザーを越えては共有しない。

1. **部屋（名前付きセッション、スレッドモードで使う）**: 会話は
   名前付きのセッションに分かれる。記録は
   `conversations/<session_id>.jsonl` に分かれ（ID はファイル名に
   安全な形へ正規化される）、再開時はそのセッションの過去の発話
   だけを履歴へ復元する。CLI は `chat --session <名前>`（既定は
   `main`）、Web UI はヘッダーのセレクトで切り替え・新規作成
   できる。添付ファイルの実体は復元せず、記録に残る要約文だけが
   文脈に戻る。
2. **用事の一覧（用事の管理、相棒モードで使う）**: 用事が切り替わる
   たびに一覧へ用事を登録し、用事ごとに題名・状態（open / done）・
   最新のメモを持たせる。用事の一覧は用事の持ち主である**ユーザーごとに
   1 つ**だけを持ち、ファイルはユーザー置き場直下の `tasks.json` に
   置く（階層は テナント ＞ ユーザー ＞ 用事の一覧）。エージェントは道具
   （`list_tasks` / `create_task` / `update_task`）で用事の一覧を読み書き
   する。`list_tasks` は記録した用事を状態付きですべて返し、
   `update_task` は ID で更新できる。対話の開始時は進行中の用事を
   すべてシステムプロンプトへ注入する。
   旧仕様の部屋ごとの用事ファイル（`tasks/<部屋名>.json`）が残っている場合は、
   用事の一覧の読み込み時にそのまま本体へ取り込む。ID が衝突したら
   使われていない番号へ振り直し、取り込みが済んだ旧ファイルは
   削除する。旧データの用事に残っている余分なキー（かつての
   `room` など）は無視して読み込む。
3. **要約による圧縮（コンパクション）**: 履歴の発話数（user/assistant）が
   閾値を超えたら、古い発話をモデル自身に要約させ、
   「（これまでの会話の要約）」の 1 発話に置き換えて会話を続ける。
   閾値は環境変数 `KUMA_COMPACT_AFTER_MESSAGES`（既定 40、0 で無効）、
   残す直近の発話数は `compact_keep`（既定 10、`KUMA_COMPACT_KEEP_MESSAGES`
   でも変更可）。要約は記録にも `summary` として残り、再開時は
   「要約レコード以前の発話は圧縮済み」として復元される。要約に失敗
   したらその回は圧縮を諦め、履歴はそのまま保つ。要約は履歴を渡す前に
   行うので、API 系・CLI 系どちらのバックエンドでも同じ仕組みが働く。
4. **長期記憶（MEMORY.md）**: セッションを越えて残すべき事実はこちらに
   分ける。セッションの履歴は「部屋ごとの文脈」、長期記憶は「部屋を
   越えた事実」という役割分担にする。

## モード（会話の進め方の選択）

会話をどう進めるかは、モードとして 2 つから選べる。設定は環境変数
`KUMA_MODE` または CLI の `--mode`（`chat` / `web`、環境変数より
優先）で、値の識別子は英語のまま、画面や文面では表示名で出す
（表示名への対応付けは `config.MODE_LABELS` に集約する）。既定は
相棒モード。不正な値は既定に倒し、旧値 `both` は後方互換の
ため相棒モード（`ledger`）として扱う。

- **相棒モード**（`ledger`、既定）: 会話はひとつ。抱えている
  用事を覚えていて、一緒に進めます。部屋は 1 つ（`main`）に固定し、
  話題ごとの用事をユーザーごとに 1 つの用事の一覧（tasks.json）で分けて管理する。
  セッション ID の指定は無視される。進行中の用事はすべて注入する。
  このモードでは「部屋」は実質存在しないので、Web UI では部屋の
  選択・作成 UI 自体を表示しない（ページは起動時メタ情報
  `GET /api/meta` でモードと表示名を知り、ヘッダーに表示名を出す）。
- **スレッドモード**（`wall`）: 会話をスレッドごとに分けて、
  それぞれ独立に進めます。用事の一覧は使わず、話題は部屋の切り替え
  だけで分ける。用事系の道具は登録されず、進行中の用事の注入も
  行わない。スレッドは作成・選択・削除ができる。Web UI では
  画面上部の UI（このモードでは呼称が「部屋」から「スレッド」に
  切り替わる）から作成・選択・削除を行い、削除は
  `POST /api/sessions/delete` で記録ファイルを消してサーバー側の
  Session も破棄する。運用者は CLI の `kuma-agent threads`
  （一覧表示と `--delete`、`--tenant` / `--user` で対象を指定）
  でも扱える。削除の対象は `memory.delete_session_record` が
  一手に担い、消すのはそのスレッドの記録ファイルだけで、用事の一覧や
  長期記憶には触れない。`main` も削除でき、その場合は次に開いた
  ときに空の記録で再開する。

CLI / TUI では、相棒モードで `--session` に別の部屋が
指定されていても起動時に「部屋は main に固定されます」と 1 行
知らせる。

## 保管と保持期限

kuma-agent は将来、コンテナでサービスとして動かす想定である。その
場合、利用者はデータ置き場のファイルを自分で消すことができない。
「消すまで残る」では置き場が際限なく膨らんでしまうため、記録には
保持期限を設け、期限を過ぎたものはシステム側が自動で掃除する。

- **設定**: 保持期限は環境変数 `KUMA_RETENTION_DAYS`（既定 **90 日**、
  `Config.retention_days`）。**0 で無期限**となり、従来どおり何も
  消さない。
- **テナントごとの保持期間**: 保持期間はテナントごとに変えられる。
  データ置き場ルートの設定ファイル `retention.json` に
  `{"tenants": {"<テナント名>": <日数>}}` と書くと、そのテナント
  だけ指定の日数になる（0 でそのテナントだけ無期限）。ここに無い
  テナントは全体の既定を使う。負数や数値でない値の項目は無視して
  全体既定に倒し、ファイルが無い・壊れている場合も例外にせず
  全体の既定で動く。
- **優先順位**: 保持期間の決定は **`--days` ＞ `retention.json` ＞
  全体の既定** の順。`kuma-agent cleanup --days <日数>` はその場
  限りの上書きで、対象範囲すべてにその日数を適用する。
- **対象**: 全テナント×ユーザー置き場を走査し（`memory.cleanup_expired`）、
  次だけを掃除する。
  - 部屋の記録ファイル（`conversations/*.jsonl`）のうち、最終更新が
    期限より古いものをファイルごと削除する。
  - 用事の一覧（対象ファイル: `tasks.json` と `tasks/*.json`）のうち、
    完了（done）してから更新が期限より古い用事だけを取り除く。
    ファイル自体と進行中の用事は残す。
  - 長期記憶（MEMORY.md）と人格ファイルは対象外で、消さない。
  - 成果物（`outputs/` と `outputs/index.json`）も対象外で、消さない
    （「成果物」節の判断による）。
- **実行タイミング**: Web サーバーの起動時に 1 回自動で実行する。
  運用者は `kuma-agent cleanup` でもいつでも実行でき、
  `--dry-run` を付けると削除せずに対象の件数だけを確認できる。
  `--tenant <名前>` を付けるとそのテナントの置き場（配下の全
  ユーザー）だけを対象にでき、他のテナントには触れない。実行時は
  対象テナントと適用した保持期間を表示する。Web 起動時の自動掃除
  でも `retention.json` の指定は自然に効く。
- **壊れたデータへの態度**: 置き場が無い・読めないファイルがある等
  では落とさず、その分を飛ばして掃除を続ける。

## 能動発信

エージェントから先に発言する仕組み（`proactive.py`）。定期チェックが
走り、「言うべきことがあるときだけ」main の会話にエージェントの発言
として投稿する。言うべきことが無ければ何もしない（毎回必ず言う
仕組みではない）。

- **チェック条件（ユーザーごと）**:
  1. そのテナントの設定で能動発信が OFF なら何もしない
     （設定は次節の settings.json、既定は ON）。
  2. 本日まだ投稿していなければ、進行中の用事（tasks.json の open な
     用事）がある場合に、その一覧を伝える発言を 1 回だけ投稿する。
     用事が無ければ投稿しない。
  3. 7 日以上 open のままの用事がある場合は、その注意喚起も同じ
     発言に含める（別発言を増やさない）。
- **頻度**: 投稿は 1 ユーザーにつき **1 日最大 1 回**。投稿済みの
  日付はユーザーの置き場に `proactive_state.json`
  （`{"last_posted_on": "YYYY-MM-DD"}`）として記録する。
- **発言文**: 自然な日本語で、進行中の用事の件数と題名（最大 5 件、
  残りは件数のみ）を挙げる形にする。モデルは使わず、用事の一覧から
  組み立てる。
- **投稿の経路**: 投稿先は `conversations/main.jsonl` で、追記は
  Session が使う既存の保存経路（`Memory.append_turn`）を通す
  （`Session.post_proactive_message`）。Web サーバーが保持している
  Session があればそれを使い（履歴にも反映される）、無ければ
  一時的に Session を作って追記して破棄する。発言の記録には能動
  発信の印（`"proactive": true`）を付ける。読み込み側は role /
  content / quote 以外のキーを無視するため、復元時は通常の
  assistant 発言として扱われ、印によって記録が壊れることはない。
- **実行のきっかけ**: Web サーバーは裏側のスレッドで、起動後
  まもなく 1 回、その後は定期的に（間隔は環境変数
  `KUMA_PROACTIVE_INTERVAL_SECONDS`、既定 **300 秒**、0 以下で
  巡回しない）全テナント×全ユーザーを巡回してチェックする。
  巡回の失敗で Web サーバー自体は落とさない。運用者は CLI の
  `kuma-agent proactive` でも 1 回だけチェックを実行できる
  （`--tenant` でテナントを、`--user` でユーザーを絞れる。モデルも
  API キーも要らない経路）。
- **対象は相棒モードだけ**: 投稿内容は相棒モードの用事の一覧が
  前提である。スレッドモード（wall）では用事の一覧を使わないため、
  能動発信は結果として発言しない。
- **好みによる抑制**: 利用者の「知らせる・知らせない」の好み
  （「知らせる・知らせないの好み」節）も効く。ミュートされた用事は
  日報にもリマインダーにも出ず、静かな時間帯は日報だけを出さない。
- **定期ジョブも同じ巡回で実行する**: 巡回は用事のチェックに加え、
  定期ジョブ（「定期ジョブ」節）の期限も見る。ジョブは用事とは
  独立で、モードを問わず・静かな時間帯の対象外として扱い、
  テナントの能動発信 OFF のときだけ用事と同じく止まる。
- **投稿は通知コールバックへも渡る**: 巡回（`run_sweep` /
  `check_and_post` / `run_due_jobs`）は、会話へ投稿するたびに
  任意の通知コールバック（`notify`、テナント名・ユーザー名・
  文面を受け取る）へも文面を渡す。Telegram への配信
  （「Telegram 接続」節）と LINE への配信（「LINE 接続」節）は
  この口を使う（両方ある場合はまとめて渡す）。通知は投稿が済んだ後に
  行い、通知側の失敗で投稿や巡回を落とすことはしない。Web の
  巡回スレッドと CLI の `kuma-agent proactive` の両方が、設定が
  あれば通知を結線する。

## 朝のまとめ

日報の拡張。決めた時刻に、子エージェントが「今日の予定」と
「進行中の用事」をまとめた朝の知らせを投稿する（`proactive.py`
の `_daily_message` が日報との振り分けを担う）。

- **有効化と時刻**: 環境変数 `KUMA_BRIEFING_TIME`（`HH:MM` 形式、
  既定 **07:30**、`off` で無効）。不正な値は既定の 07:30 として
  扱う。有効な間は、まとめの時刻より前に日報を投稿しない。
  時刻を過ぎた最初の巡回で朝のまとめを投稿し、その日の声かけ枠
  （1 日 1 回）を使う。`off` のときは従来どおり、その日の最初の
  巡回で日報を投稿する。
- **組み立て**: 委任の仕組み（「委任」節）で子セッションに任せる。
  子への指示には、その日の日付と、進行中の用事の一覧（ミュート
  された話題を除いたもの）を含め、「カレンダーを確認できる道具
  があれば今日の予定を確認すること」「予定も用事も無ければ
  『なし』とだけ答えること」「あれば挨拶と今日の予定（時刻と
  題名）と用事を短くまとめること」を伝える。子の文章がそのまま
  投稿文になる（能動発信の印と Telegram 配信も日報と同じ経路）。
- **子を動かす条件**: 進行中の用事がある、または、そのユーザー
  のセッションの道具にカレンダーらしい道具（名前に `list-events`
  を含むもの。Google カレンダーの `gcal__list-events` を想定）が
  あること。どちらも無ければ従来どおり何もしない。
- **結果の扱い**:
  - まとめの文章が返れば、それを投稿して声かけ枠を使う。
  - 「なし」が返れば投稿しない。代わりに「今日は確認済み」
    （`proactive_state.json` の `briefing_checked_on`）を記録し、
    その日は子を二度と動かさない（声かけ枠は消費しない）。
  - 子が失敗（例外・error の結果・空応答）したら、用事がある
    場合は従来の日報の文面に倒す（声かけ自体は欠かさない）。
    用事が無ければ何もしない。
- **既存の規則との関係**: テナントの能動発信 OFF のときは動か
  ない。静かな時間帯は日報と同じく止める（枠も消費しない）。
  実行順は ジョブ → リマインダー → 朝のまとめ／日報 の位置づけ
  を保つ。モデルなしの一時 Session で巡回する経路（CLI の
  `kuma-agent proactive`）では子を動かさず、従来の日報の組み
  立て（モデルなしでできる）だけを行う。手動実行である同
  コマンドは、まとめの時刻より前でも日報を出す（自動巡回は
  時刻まで待つが、運用者の「今すぐ出す」判断を優先する。
  その場で出した日報はその日の声かけ枠を使う）。

## リマインダー（時刻指定の通知）

用事に通知時刻を持たせ、時刻が来たら能動発信の巡回が知らせる仕組み。

- **用事の項目**: `Task` に `remind_at`（通知時刻、ISO 8601 文字列、
  空なら未設定）と `reminded_at`（通知済み時刻、空なら未通知）を
  追加した。旧形式の `tasks.json`（項目なし）はそのまま読める
  （欠けた項目は未設定・未通知として扱う）。
- **道具**: `create_task` / `update_task` が `remind_at` を受け取る。
  `update_task` で空文字列を渡すと通知時刻を取り消す。通知時刻が
  変わったら通知済みの印は消え、新しい時刻で改めて通知される。
  `list_tasks` の表示と、相棒モードでプロンプトに注入される用事
  一覧には、通知時刻があれば「（11/3 9:00 に通知）」の形で含める。
- **時刻の解釈**: サーバーのローカルタイムゾーン基準。オフセット
  なしの ISO 文字列はローカル時刻として解釈し、オフセット付きは
  ローカル時刻へ変換して比較する。モデルが「明日9時に知らせて」を
  絶対時刻に直せるよう、システムプロンプトには発話のたびに現在
  日時（ローカル時刻、曜日つき）を添える。
- **巡回での判定**: open な用事で `remind_at` が現在時刻以下かつ
  未通知のものがあれば、件数と題名を挙げる発言（複数の場合は
  1 件にまとめる）を main の会話へ投稿し、`reminded_at` を記録
  して二度と通知しない。完了した用事（done）は通知しない。
- **日報との関係**: リマインダーは利用者が時刻を指定した依頼なの
  で、日報の「1 日 1 回まで」の上限とは独立に発言する（日報を
  投稿済みの日でも発言する）。同じ巡回で両方が立つ場合は
  リマインダーを先に投稿する。
- **テナント設定との関係**: 能動発信が OFF のテナントでは
  リマインダーも通知しない。スレッドモードでも同様に発言しない。

## 定期ジョブ

決まった予定で指示文を自動実行する仕組み（`jobs.py`）。日報や
リマインダーが「用事の一覧」から発言文を組み立てるのに対し、
こちらは登録された指示文そのものをエージェントに実行させる
汎用の定期実行である。

- **保存形式**: ユーザーの置き場に `jobs.json` を置き、ジョブの
  配列を保持する。1 件の項目は `id`、`title`（名前）、`prompt`
  （実行する指示文）、`schedule`（予定）、`enabled`（有効かどうか、
  既定は true）、`last_run_at`（前回実行時刻、未実行なら空）、
  `created_at`（作成時刻）。ファイルが無い・壊れている場合は
  空の一覧として動き、壊れたレコードは読み飛ばす。
- **予定の形式**: `schedule` は次の 3 種だけ。
  - `{"kind": "daily", "time": "09:00"}`: 毎日その時刻
  - `{"kind": "weekly", "weekday": 0, "time": "09:00"}`: 毎週その
    曜日（weekday は月曜=0 〜 日曜=6）
  - `{"kind": "interval", "hours": 6}`: 前回実行からその時間ごと
  種別に要らない項目を一緒に渡した組み合わせも不正として弾く
  （意図と違う予定で登録されないように）。
- **期限判定**（`jobs.is_due`）: daily / weekly は、基準時刻
  （`last_run_at`、未実行なら `created_at`）より後に来た直近の
  予定時刻が現在時刻以下なら期限が来ている。interval は基準時刻
  + hours が現在時刻以下なら期限が来ている。複数回分を逃しても
  判定は真偽値だけなので、実行は 1 回だけになる（追いつき実行は
  しない）。無効（`enabled` でない）ジョブは実行しない。
- **実行の仕組み**: 能動発信の巡回（`proactive.run_sweep` /
  `check_and_post`）がテナント×ユーザーを回る流れの中で、期限の
  来たジョブを委任の仕組み（「委任」節、`delegate` の子セッション）
  で実行する。子は親と同じ人格・道具構成で指示文を受け取り、
  最終応答が結果になる。結果はそのユーザーの main の会話へ
  「定期ジョブ「{title}」の結果です。」の見出し付きで投稿し、
  記録には能動発信の印（`proactive: true`）を付ける（日報等と
  同じ経路、`Session.post_proactive_message`）。
- **失敗時の扱い**: 実行したら成功・失敗にかかわらず
  `last_run_at` を実行時刻に更新する（同じ予定で繰り返し実行
  しないため）。失敗時（子の例外・時間切れ・error の結果）は、
  結果の代わりに短い失敗の知らせを main の会話へ投稿する。
  1 件の失敗で巡回全体は落とさない。なお、モデルなしで巡回する
  経路（CLI の `kuma-agent proactive`）ではジョブは実行せず、
  失敗としても消費しない（実行できる経路の巡回に委ねる）。
- **能動発信 OFF との関係**: テナントの設定で能動発信が OFF
  （`settings.json` の `proactive_enabled`）なら、ジョブも実行
  しない。静かな時間帯はジョブには適用しない（リマインダーと
  同じ扱い。予定そのものが実行の依頼であるため）。ミュートの
  好みもジョブには効かない（対象は用事の題名・メモであり、
  ジョブは名前で ON/OFF を管理する）。
- **モードとの関係**: モードは問わず動作する。用事の一覧を
  前提にする日報・リマインダーが相棒モードだけなのに対し、
  ジョブはスレッドモードでも実行し、結果は main の会話へ届く。
- **管理の入口（道具と CLI）**: 会話からは道具で管理する
  （モードを問わず登録する）。`create_job`（title / prompt /
  kind / time / weekday / hours。不正な組み合わせは error）、
  `list_jobs`（名前・予定・ON/OFF・前回実行の一覧）、
  `delete_job`（名前または ID で削除）、`set_job_enabled`
  （名前または ID と enabled で ON/OFF）。作業中表示は
  `list_jobs` が「定期ジョブを確認中」、他が「定期ジョブを記録中」。
  運用者は CLI の `kuma-agent jobs`（`--tenant` / `--user` で
  対象を指定、API キー不要）で一覧を確認できる。

## 知らせる・知らせないの好み

能動発信に対する利用者ごとの好み（`notify_prefs.py`）。「その話題は
知らせないで」「夜は静かにして」という希望を覚えて、巡回の発言を
抑える仕組み。

- **保存形式**: ユーザーの置き場に `notify_prefs.json` を置き、形式は
  `{"muted_topics": ["語", ...], "quiet_start": "22:00",
  "quiet_end": "07:00"}`。ファイルが無い・壊れている場合は
  「好みなし」として動く（壊れた項目はその項目だけ無かったことに
  する）。テナント設定（settings.json）がテナント単位なのに対し、
  こちらはユーザー単位である。
- **ミュート（知らせない話題）**: 用事の題名＋メモに、muted_topics の
  いずれかの語が（大小文字を区別せず）部分一致したら、その用事は
  日報にもリマインダーにも出さない。日報で全件ミュートされたら
  日報は発言しない。リマインダーがミュートされた場合は、通知済み
  の印（reminded_at）を付けずに保留する。ミュートを外せば、後の
  巡回で改めて通知される。
- **静かな時間帯**: quiet_start〜quiet_end の間は日報（定期の用事
  まとめ）だけを出さない。開始を含み終了を含まず、日をまたぐ範囲
  （22:00〜07:00 など）も正しく扱う。開始と終了が両方そろって
  正しく読めるときだけ有効で、開始 == 終了は時間帯なしとして扱う。
  時間帯に入っている間は日報の「投稿済み」記録（proactive_state
  .json）を消費しないため、時間帯が明ければその日の日報を出せる。
- **リマインダーとの違い**: リマインダーは利用者が時刻を指定した
  依頼なので、静かな時間帯でも出す（止めるのは日報だけ）。ただし
  ミュートはリマインダーにも効く。時刻を指定したうえで、その話題
  自体を知らせないでほしい、という希望は両立するためである。
- **学習の入口（道具）**: 会話の中で好みを覚える道具を用事系と同じ
  条件（相棒モード）で出す。`set_notify_mute`（知らせない語の登録。
  「その話題は知らせないで」と言われたらモデルが呼ぶ）、
  `clear_notify_mute`（登録を外す）、`list_notify_prefs`（現在の
  好みを返す）。作業中表示は「知らせ方の設定を更新中／確認中」。
- **Web UI**: テナント管理パネル内の「知らせ方の好み（現在の
  ユーザー）」の節で、現在のテナント×ユーザーのミュート一覧の
  表示・追加・削除と、時間帯の入力・保存・解除ができる。API は
  `GET /api/notify_prefs`（tenant / user を受ける）と
  `POST /api/notify_prefs`（add_topic / remove_topic の追加・削除、
  quiet_start / quiet_end の設定・解除。両方 null で解除）。

## テナント設定と管理

テナントごとの振る舞いの設定と、テナントの作成は Web UI の
「テナント管理」パネルと API で扱う。

- **設定ファイル（settings.json）**: データ置き場ルートに置き、形式は
  `{"tenants": {"<テナント名>": {"proactive_enabled": true/false,
  "approvals_enabled": true/false}}}`
  （`settings.py` が読み書きする）。ファイルが無い・壊れている場合や、
  そのテナントの指定が無い場合は既定値で動く（能動発信も承認も
  **ON**）。値が真偽値でない項目は無視する。保存時は他のテナントの
  指定や同じテナントの他の項目を壊さない。
- **保持期間の設定も同じ画面から**: 保持期間のテナント別指定は
  従来どおり `retention.json` の仕組み（「保管と保持期限」節）を
  そのまま使い、設定 UI から読み書きできるようにした（保存関数は
  `memory.save_retention_override`、null で指定を取り除いて全体の
  既定に戻す）。
- **Web API**:
  - `GET /api/tenant_settings?tenant=<名前>` →
    `{tenant, proactive_enabled, approvals_enabled,
    retention_days（未設定なら null）,
    retention_effective_days（全体の既定まで含めた実効値）}`
  - `POST /api/tenant_settings` `{tenant, proactive_enabled?,
    approvals_enabled?, retention_days?（null で未設定に戻す）}` →
    保存して最新の設定を返す。渡されていない項目は変更しない。
    型が違う値や負の日数は 400 で返す。
  - `POST /api/tenants/create` `{name}` → テナント名を既存の正規化
    （`normalize_tenant_name`）で検証し、`tenants/<名前>` の置き場を
    作る。空の名前・既定テナント（`default`、作成済みとして扱う）・
    すでに存在する名前は 400 で理由を返す。作成できたら正規化後の
    名前を返す。
  - `POST /api/tenants/delete` `{tenant}` → テナントを削除する
    （手順は下記の「テナントの削除」参照）。既定テナントと起動時
    テナントは 400、置き場が無いテナントは 404 で理由を返す。
- **Web UI**: ヘッダーの「テナント管理」ボタンでパネル（展開
  セクション）を開く。テナントごとに、能動発信の ON/OFF トグル、
  承認確認の ON/OFF トグル、保持期限（日数）の入力欄と保存ボタン、
  そのテナントへの切替ボタンを出す。新規作成は名前入力＋作成
  ボタンで、成功したら一覧とヘッダーのテナント切替 UI に反映
  され、そのテナントへ切り替わる。削除ボタンは既定テナント以外
  の行に出る（下記参照）。
- **テナントの削除**: 削除は取り消せないため、段取りを厳密に守る。
  - **確認**: 画面ではテナントごとの「削除」ボタンを押し、確認
    としてテナント名の入力を求める（入力が一致しないと進めない）。
    既定テナント（`default`）の行には削除ボタンを出さない。
  - **削除できない対象**: 既定テナントは置き場がデータ置き場
    そのものであるため、API でも削除を拒否する。サーバーの起動時
    テナントも、土台となる UserStore を抱えているため削除できない
    （どちらも 400）。置き場が無いテナントは 404。
  - **手順**: (1) そのテナントの全データの控えを、データ置き場
    ルートの `backups/tenant-<名前>-<日時>.zip` に保存する
    （`export.save_tenant_backup`。テナントの全ユーザー分を置き場
    からの相対パスのまま収め、先頭に控えである旨とテナント名・
    ユーザー一覧を入れる）。控えが作れなければ削除しない。
    (2) テナントの置き場（`tenants/<名前>`）を丸ごと削除する。
    (3) 置き場の外にあるテナント設定（`settings.json` と
    `retention.json` のそのテナントの項目）を取り除き、サーバーが
    抱えているそのテナントの UserStore も破棄する（消えたテナント
    が一覧に残ったり、置き場が作り直されたりしないように）。
  - 削除の入口は Web のみで、CLI には用意しない（テナントの作成
    も Web のみのため）。能動発信の巡回はテナントを置き場から
    列挙するため、消えたテナントは巡回の対象からも自然に外れる。

## 作業中表示（UI）

LLM の応答や道具の実行には時間がかかることがあるため、UI には
「今なにをしているか」をアニメーション付きで出す。頭文字のような
記号表示ではなく、実際の作業に応じた文言にする。

- **中核（Session）**: `Session.on_status` コールバックが対話ループの
  各段階で現在の作業を通知する。モデルへの問い合わせ開始時は
  「考え中」、道具の実行直前は道具ごとの作業名（`tools.activity_label`:
  例えば read_file は「ファイルを読んでいます」で、ファイル名など
  安全な手がかりがあれば添える）、要約圧縮の実行時は「会話を要約中」。
  応答が終わったら空文字列を通知して表示なしに戻す。CLI 系
  バックエンドでも問い合わせは同じ経路を通るので同じ表示が出る。
- **Web UI**: サーバー側で部屋ごとの現在の状態を保持し、
  `GET /api/status`（tenant / user / session の指定に対応）で返す。
  ページは送信中ポーリングで状態を取り、入力欄の上に「うごめく点＋
  状態文言」の行を表示し、応答が返ったら消す。
- **TUI**: 応答待ちの間は `Session.say` を別スレッドで実行し、入力欄の
  上の行に状態文言とフレームごとに変わる点を出し続ける。待ち中も
  ログのスクロール（PageUp / PageDown）と終了は受け付ける。
- **プレーンな CLI**: 状態をキャリッジリターンで同じ行に上書き表示し、
  応答前に行を消す簡易表示。

## Web UI のタブ構成（2026-11-04）

画面はタブ方式にし、上部にタブバー（会話／フィード／アイデア／
目標／探す／管理）を置く。既存の画面の移し先は次のとおり。

- **会話**: 会話ログ、入力欄、承認の確認。従来どおりの対話画面。
- **探す**: 成果物の一覧（従来の「成果物」パネル）。
- **管理**: 管理メニュー（ボタン集）から、テナント管理・人格／記憶・
  使用量の各パネルと、書き出し・復元を使う。
- **フィード／アイデア／目標**: 器だけ先に用意し、中身は順に入れる
  （フィード＝能動発信と用事の進み具合の時系列、アイデア＝提案の
  カード、目標＝長期の目標と進捗）。当面は「準備中」の表示。

ヘッダーには、テナント／ユーザー／部屋の選択とテーマ（昼／夜／
システム／8ビット）を残す。8ビットはインベーダーゲーム風の見た目で、
黒い宇宙（星空つき）に緑のドット、角をなくし枠を太くし、影をベタ影に
する。テーマは
ヘッダー右上のアイコンボタンで巡回して切り替え（いまのテーマの
アイコンを表示）、CSS 変数＋ `data-theme`
で効かせる。選択はブラウザの localStorage に保存する
（ログイン画面にも適用）。

アバターを押すと「いまの状況」パネルが開く。状態（`/api/status`、
用事の総数・未完了数つき）、承認待ちの有無、頭脳の使用量（累計）、
いまの場所（テナント／ユーザー／部屋）をまとめ、開いている間は
数秒ごとに取り直す。

見た目の方針（2026-11-04 追加）: ボタンは文字ではなくアイコンで
示す（意味は title と aria-label で伝える）。角の丸みは控えめに
して全体を少し角ばった印象にする。スマホ幅（720px 以下）では

発話の操作ボタン（2026-11-04 変更）: 引用・読み上げ・リアクション

## MCP 対応

MCP（Model Context Protocol）のクライアント（`mcp_client.py`）。
外部の MCP サーバーが提供する道具を、組み込み道具と並べて頭脳に
渡す。実装は標準ライブラリだけで、新規依存は入れない。

- **設定（mcp.json）**: 形式は
  `{"servers": [{"name": ..., "command": ..., "args": [...],
  "env": {"K": "V"}}]}`。置き場はデータ置き場ルートが既定で、
  テナントの置き場（`tenants/<名前>/`。既定テナントはルート
  そのもの）に `mcp.json` があれば、そのテナントは**そちら
  だけ**を使う（ルートの設定とは混ぜない。テナント側の
  ファイルが壊れていれば、そのテナントでは MCP 道具が出ない
  だけで、ルート側には倒れない）。どちらのファイルを使うかは
  セッション作成時に決まり、内容はマネージャ生成時に一度
  だけ読むため、設定の追加・変更の反映には再起動が要る。
  ファイルが無い・壊れている・項目が不正な場合は、その
  サーバー（または全体）を無効として静かに動く（例外で落と
  さない）。サーバーへ渡す環境変数は、設定で指定した分に
  最小限（`PATH`・`HOME`）を加えたもの。
- **トランスポートは stdio のみ**: サーバーを子プロセスとして
  起動し、改行区切りの JSON-RPC 2.0 で会話する。HTTP 系の
  トランスポートには対応しない。
- **プロトコルは従来方式（2025 世代）**: `initialize`
  （protocolVersion は `2025-11-25` を送り、サーバーが返した版を
  受け入れて進める）→ `notifications/initialized` →
  `tools/list` → `tools/call` の流れで話す。2026-07-28 版
  （いわゆる v2）のサーバーも従来方式のクライアントを受け付ける
  ため、これで新旧両方のサーバーにつながる。サーバー起点の
  リクエスト（sampling 等）には対応せず、メソッド不明のエラー
  で返す。
- **道具の統合**: 道具名は `<サーバー名>__<道具名>` と前置して
  組み込み道具との衝突を避ける。説明文と入力スキーマ
  （inputSchema）はサーバーのものをそのまま頭脳へ渡す。実行
  結果は content のテキストブロックを連結した文字列にし、
  テキスト以外のブロックはその旨を短く記す。`isError` の結果と
  JSON-RPC エラー（存在しない道具への `-32602` を含む）は、
  モデルに失敗と分かる形の結果文字列にする（例外で会話を落と
  さない）。作業中表示は「道具を使っています（<サーバー名>）」
  という汎用表示にする。
- **道具が効く頭脳**: 組み込み道具が効く API 系の頭脳
  （muse / claude / gemini）でのみ MCP 道具も出す。CLI 系の
  頭脳は道具ループを自前で管理するため、組み込み道具と同じく
  MCP 道具も出さない（そちらの MCP 対応は各 CLI 自身の設定の
  領分）。
- **プロセス管理**: サーバーは遅延起動（最初に道具一覧が必要に
  なった時点）し、プロセスは使い回す。接続は実効の設定の
  置き場単位で共有する（`get_shared_manager`）ため、Web 経路
  でも全セッションで共有され、部屋ごとに複製されない。
  テナント別設定を使うテナント同士、およびルート設定を使う
  組み合わせとは別のマネージャ（＝別のサーバープロセス群）
  になり、道具やプロセスが混ざらない。呼び出しはサーバー
  ごとに直列化し、応答待ちには
  タイムアウト（既定 60 秒、環境変数 `KUMA_MCP_TIMEOUT_SECONDS`）
  を付ける。タイムアウトやプロセス終了時はその道具を失敗と
  して扱い、接続を捨てて次回の呼び出しで再起動を試みる。
  終了処理は atexit（Web サーバーは serve の終了時にも明示）
  で子プロセスを止める。
- **セキュリティ注意**: MCP サーバーの設定は任意のコマンド
  実行と同義である。設定ファイルを用意できるのは運用者だけ
  という前提に立ち、利用者が画面から追加する経路は作らない。
- **将来課題**: HTTP 系トランスポート、サーバー起点
  リクエストへの対応。

### ブラウザ操作（Playwright MCP）

ブラウザ操作は専用の実装を持たず、MCP サーバーに任せる。
Microsoft の Playwright MCP サーバーを `mcp.json` に登録する
だけで、会話から Web サイトを開いて操作できることを
2026-11-02 に実証した。設定例（サーバー名は `browser`）:

```json
{"servers": [{"name": "browser", "command": "npx",
  "args": ["-y", "@playwright/mcp@<版番号>", "--headless"],
  "env": {}}]}
```

- **実証内容**: 登録すると道具が 25 個出る
  （`browser__browser_navigate` など）。ローカルのテスト
  ページで、ページを開く・スナップショットを取る・ボタンを
  クリックして表示が変わる・入力欄に文字を入れる、までを
  確認した。サーバーは従来方式のハンドシェイク
  （2025-11-25）で応答し、このクライアントで問題なく
  つながった。
- **版の固定と初回の遅さ**: `@latest` を付けると起動のたびに
  最新版の確認が走って遅くなることがあるため、例のように
  版を固定する。初回は npx のパッケージ取得で起動が遅く、
  道具が一覧に出ないことがある。一度手で実行して取得を
  済ませておくと安定する。
- **サンドボックス**: コンテナ等の環境では Chromium の
  サンドボックスが原因で起動に失敗することがある。その
  場合は引数に `--no-sandbox` を足す。既存の Chromium を
  使う場合は `--executable-path` で指定できる。
- **状態の残り方**: ブラウザはサーバー側（共有マネージャの
  子プロセス）で動き続けるため、開いたページの状態は会話を
  またいで残る。閉じる操作をしない限り、別の部屋の会話から
  も同じページが見える点に注意する。
- **承認**: MCP の道具なので、危険な操作の承認の仕組みが
  そのまま効く（承認が有効な環境ではブラウザ操作ごとに承認
  が挟まる）。`browser_run_code_unsafe` のような強い道具も
  含まれるため、承認は有効にしておくのが望ましい。
- **頭脳の範囲**: 道具が出るのは API 系の頭脳だけ（MCP の
  既存仕様どおり）。
- **コンテナでの利用**: Docker イメージには Node.js と
  Chromium、Playwright MCP サーバーが導入済みのため、
  コンテナでもそのまま使える（0.39.0 から。「コンテナで
  動かす」節も参照）。コンテナでは npx の初回取得を待たず
  コマンド名で直接起動し、同梱ブラウザではなくシステムの
  Chromium を使う。`mcp.json` はデータ置き場ルート
  （コンテナでは `/data/mcp.json`）に置く。設定例:

```json
{"servers": [{"name": "browser", "command": "playwright-mcp",
  "args": ["--headless", "--no-sandbox",
           "--executable-path", "/usr/bin/chromium"],
  "env": {}}]}
```

### 実サービスの接続例（Google カレンダー）

実サービスも専用の実装を持たず、MCP サーバーに任せる。
Google カレンダーの MCP サーバー（`@cocal/google-calendar-mcp`、
nspady の google-calendar-mcp の現在の npm 名）を `mcp.json`
に登録し、OAuth 認証情報ファイルの場所を環境変数で渡す形で
つなげることを 2026-11-02 に実証した。設定例（サーバー名は
`gcal`、確認時の版は 2.8.1）:

```json
{"servers": [{"name": "gcal", "command": "npx",
  "args": ["-y", "@cocal/google-calendar-mcp@2.8.1"],
  "env": {"GOOGLE_OAUTH_CREDENTIALS": "</path/to/gcp-oauth.keys.json>"}}]}
```

- **実証内容**: 登録すると道具が 13 個出る
  （`gcal__list-events`、`gcal__create-event`、
  `gcal__delete-event`、`gcal__get-freebusy`、
  `gcal__manage-accounts` など）。サーバーは従来方式の
  ハンドシェイク（2025-11-25）で応答し、このクライアントで
  問題なくつながった。認証情報ファイルがあれば（中身が
  本物でなくても）サーバーは起動して道具一覧は出ることも
  確認した。ただし実際に予定を読むには本物の認証が要り、
  未認証で道具を呼ぶと認証を促すエラーが返る。
- **利用者側の準備**: (1) Google Cloud Console でプロジェ
  クトを作り、Google Calendar API を有効化し、OAuth
  クライアント（デスクトップアプリ）を作成して
  `gcp-oauth.keys.json` をダウンロードする。(2) そのファ
  イルのパスを設定例のように `GOOGLE_OAUTH_CREDENTIALS`
  で渡す。(3) 初回だけ
  `npx @cocal/google-calendar-mcp auth` を一度実行して
  ブラウザで Google にサインインする（道具
  `gcal__manage-accounts` の add でもよい）。ここまで済むと
  予定の読み書きができる。
- **同意画面と 7 日失効**: OAuth 同意画面が「テスト」の
  ままだと更新トークンは 7 日で失効する。継続して使うには
  同意画面を公開（本番）にする。
- **版の固定と初回の遅さ**: ブラウザ操作の小節と同じ注意
  があてはまる。`@latest` ではなく版を固定し、初回は npx
  のパッケージ取得で起動が遅く道具が一覧に出ないことが
  あるため、一度手で実行して取得を済ませておくと安定する。
- **秘密情報の置き場所**: `gcp-oauth.keys.json` とトークン
  （サーバー側の既定で
  `~/.config/google-calendar-mcp/tokens.json`）は認証情報
  そのものである。運用者の管理下に置き、リポジトリには
  含めない。コンテナでは後述のとおり両方ともデータ
  ボリューム（`/data`）に置く形になるため、その場合は
  ボリューム自体を秘密情報として扱う。
- **承認**: MCP の道具なので、危険な操作の承認の仕組みが
  そのまま効く。予定の作成・変更・削除も承認の対象になる
  （実データを書き換える操作なので、安全上むしろ望ましい）。
- **頭脳の範囲とコンテナ**: 道具が出るのは API 系の頭脳
  だけ（MCP の既存仕様どおり）。Docker イメージには
  Node.js とこのサーバーが導入済みのため、コンテナでも
  そのまま使える（0.39.0 から）。コンテナではコマンド名で
  直接起動し、認証まわりのファイルはすべてデータ
  ボリューム（`/data`）配下に置く。設定例（`mcp.json` は
  `/data/mcp.json`）:

```json
{"servers": [{"name": "gcal", "command": "google-calendar-mcp",
  "args": [],
  "env": {"GOOGLE_OAUTH_CREDENTIALS": "/data/gcp-oauth.keys.json"}}]}
```

  コンテナの `HOME` は `/data/home` にしてあるため、トークン
  は `/data/home/.config/google-calendar-mcp/tokens.json` に
  保存され、コンテナを作り直しても認証は消えない。初回認証
  （ブラウザでの Google サインイン）はホスト側で
  `npx @cocal/google-calendar-mcp auth` を実行して済ませ、
  できた `~/.config/google-calendar-mcp/tokens.json` を
  ボリューム内の `/data/home/.config/google-calendar-mcp/`
  に置くのが実用的な経路である（`gcp-oauth.keys.json` は
  `/data` 直下に置く）。

## 承認（危険な操作の確認）

危険な道具は、実行前に利用者の承認を挟む。承認の確認は
`ToolBox.approval_check` フックが担い、`Session` がテナント設定と
UI 側の承認者（`Session.approver`）を配線する。

- **対象の道具**: `run_shell`（任意のコマンド実行）と、すべての
  MCP 道具（名前に `__` を含むもの。外部サーバーが実体を持つ
  ため一律で対象にする）。それ以外（ファイル読み書き、用事、
  記憶など）は v1 では承認なしで実行する。分類は
  `tools.requires_approval` に集約する。
- **テナント設定**: `settings.json` の `approvals_enabled`
  （既定は **true** ＝承認を挟む）。false のテナントでは承認を
  一切挟まず従来どおり実行する（承認者は呼ばれない）。読み書きは
  `settings.py`、Web では `GET/POST /api/tenant_settings` の項目と
  テナント管理パネルの「承認確認」トグルで扱う。
- **結果の返し方**: 承認はフックが True を返すまで実行しない。
  却下された場合は例外ではなく道具の結果文字列
  `error: 承認されませんでした` をモデルへ返し、会話は続く。
  承認の要否と結果は作業中表示にも出す（「承認を待っています
  （<道具名>）」「承認されませんでした」）。
- **経路ごとの承認者**:
  - **Web**: `ApprovalBroker` が保留中の承認をテナント×ユーザー
    単位で保持し、会話リクエストのスレッドは決定まで待つ。
    `GET /api/approvals`（保留一覧: id・道具名・引数の要約・時刻）
    と `POST /api/approvals/decide`（`{id, approved}`）で画面が
    扱い、画面には状態ポーリングに相乗りして保留が表示され、
    「許可」「却下」ボタンで決められる。引数の要約は
    `tools.summarize_tool_args`（run_shell はコマンド文字列、
    長すぎる場合は切り詰め）。
  - **プレーン CLI（chat）**: 標準入力で y/N を尋ねる。Enter のみ、
    y 以外、EOF はすべて却下。端末の前に人がいてプロンプト自体
    が待ちになるため、この経路に時間切れは設けない。
  - **TUI**: say のワーカーが承認待ちになると、状態行に対象と
    引数の要約と答え方を出し、入力欄を y/n の回答欄として使う
    （Enter で決定）。承認待ちであることは画面で分かる。
- **タイムアウトと安全側の既定**: Web / TUI の承認待ちには上限
  （既定 300 秒、環境変数 `KUMA_APPROVAL_TIMEOUT_SECONDS`、
  0 以下は既定値として扱う）があり、時間切れは却下として扱う。
  承認者が接続されていない経路（テストや組み込み利用）で承認が
  必要になった場合も、安全側に倒して常に却下する。承認者の
  例外も却下として扱う。

## 長期記憶の検索

長期記憶（MEMORY.md）は育つと全文をプロンプトへ載せきれなくなるため、
キーワード検索の道具と、注入の切り替えを用意する。

- **分割単位**: MEMORY.md を項目単位に割る（`memory.split_memory_segments`）。
  見出し行（`#`）と箇条書き行（`- ` など）が項目の始まりで、それ以外の
  行は直前の項目への続き行として取り込み、空行は区切りになる。各断片は
  開始行（1 始まり）を保持し、出どころとして使う。これは MEMORY.md の
  実際の書式（`remember` が 1 行 1 件の箇条書きで追記し、利用者が
  見出しを足すこともある）に合わせた分割である。
- **照合方式**: クエリを空白・句読点で語に分け、各語の部分文字列一致で
  断片を点数付けする。点数は「一致した語の数」を主、「語の出現回数」を
  副とし、同点は行の早い順に並べる。形態素解析や外部ライブラリは
  使わない。日本語の文章は分かち書きされないため、部分一致が前提になる。
- **道具 `search_memory`**: 引数は `query` と任意の `limit`（既定 5）。
  結果は点数の高い順に最大 limit 件、各断片に「MEMORY.md の N 行目」
  という出どころを付けて返し、0 件なら「見つかりませんでした」と返す。
  作業中表示は「記憶を検索中」。道具が出る範囲は用事系の道具と同じ
  （相棒モードで、API 系の頭脳の道具ループに載る）。CLI の
  `kuma-agent memory-search <クエリ>`（`--tenant` / `--user` 指定可、
  API キー不要）でも同じ検索ができる。
- **注入の切り替え**: 記憶が閾値（環境変数
  `KUMA_MEMORY_FULL_INJECT_CHARS`、既定 6000 文字）以下なら従来どおり
  全文を注入する。超えたら新しい方（末尾側）の項目から閾値に収まる分
  だけを注入し、「一部のみ表示しています。残りは search_memory で
  検索できます」という趣旨の一文を添える（`memory.memory_inject_text`）。
  切り捨ては項目の途中で切らない。1 項目だけで閾値を超える場合は、
  その項目を丸ごと入れる（直近の記憶を失わないため）。スレッドモード
  では検索道具自体を出さないため、案内文は一部表示であることだけを
  伝える形にする。

## 長期記憶の整理

育った長期記憶（MEMORY.md）の重複や古い言い回しを整える仕組み
（`memory_tidy.py`）。整理は 2 段構えで、適用の前には必ず
バックアップを残す。

- **1 段目: 機械的な重複除去（モデル不要・情報損失なし）**:
  `memory.split_memory_segments` の項目単位で判定し、空白や
  前後の記号を正規化して「実質同じ項目」が複数ある場合は
  最初の 1 つだけを残す（順序は保ち、項目の途中で切らない）。
  見出し行そのものは対象にしない。異なる項目の本文には
  一切触れないため、この段だけで情報が失われることはない。
- **2 段目: モデルによる統合（任意実行）**: 設定済みの頭脳へ
  道具なしの単発 chat で 1 回だけ問い合わせ、現在の MEMORY.md
  全文を渡して「重複をまとめ、関連する項目を統合し、古い
  言い回しをそろえた全文」を返させる。統合用の指示には
  「事実・日付・固有名詞を落とさないこと、書かれていないこと
  を補わないこと、見出しと箇条書きの形式を保つこと」を含める。
  応答が空、または元の 2 割未満の長さしかない場合は失敗と
  して扱い、機械的除去の分も含めてファイルは変更しない。
- **バックアップ**: 本体を書き換える場合は、その前に必ず
  元の全文を同じ置き場の `MEMORY.md.bak-<日時>` へ残す
  （同じ日時のものがある場合は連番を付けて上書きを避ける）。
  変更が無い場合（すでに整理済み、除去できる項目が無い場合）
  は書き込まず、バックアップも作らない。
- **入口は 3 つ**:
  - **CLI `kuma-agent memory-tidy`**（`--tenant` / `--user`
    で対象を指定）: 機械的除去→モデル統合の順で適用し、
    バックアップ先と前後の行数を表示する。モデルが要るため
    API キー必須のコマンドとして配置する。`--dry-run` では
    本体を変更せず、提案を `MEMORY.md.proposed` に書き出して
    差分行数だけを表示する（提案を作るのにもモデルが要る
    ため、こちらも API キー必須）。
  - **道具 `tidy_memory`**: 記憶系の道具と同じ条件（相棒
    モード）で登録し、モデル統合まで実行してバックアップを
    残して適用する。結果は「N行→M行に整理しました
    （バックアップ: ファイル名）」の形で返し、作業中表示は
    「長期記憶を整理中」。
  - **自動の機械的除去**: 能動発信の巡回（`proactive`）の
    中で、ユーザーの MEMORY.md が大きい場合（全文注入の
    上限 `KUMA_MEMORY_FULL_INJECT_CHARS` の **3 倍**を超える）
    だけ、**1 日 1 回まで**機械的な重複除去を自動適用する。
    実施日はユーザーの置き場の `memory_tidy_state.json`
    （`{"last_auto_tidy_on": "YYYY-MM-DD"}`）に記録する
    （proactive_state.json と同じ流儀）。除去できる項目が
    無かった日もチェック済みとして記録する。適用しても
    会話へは投稿しない。テナントの能動発信が OFF のときは
    巡回自体が動かないため、自動除去も行わない。
- **モデル統合は自動では行わない**: モデル統合は費用がかかる
  うえに、本文の言い回しまで書き換える判断を伴う。裏側で
  勝手に行わず、利用者や運用者が CLI・道具で明示的に頼んだ
  ときだけ実行する。自動で安全にできるのは、情報損失の
  ない機械的除去だけに限る。
- **何もしない場合**: 記憶が無い・空の場合は、どの入口でも
  エラーにせず何もしない。自動除去は記憶が小さい場合も
  対象外（状態ファイルも作らない）。

## 長期記憶の自動抽出

会話の中で道具（remember）を使って書き留める以外に、新しい
会話から「長期記憶に残すべきこと」を裏側で自動的に抜き出して
MEMORY.md へ足す仕組み（`memory_extract.py`）。モデル統合
（整理）と違い、こちらは自動実行が本筋で、本文の書き換えは
せず末尾への追記だけを行う。

- **材料と処理済み位置**: 対象は前回の抽出以降に増えた会話の
  発話だけ。会話ファイルごとに「読み終えたレコード数」を
  ユーザーの置き場の `memory_extract_state.json`
  （`{"last_attempt_on": ..., "positions": {"main": N, ...}}`）
  に持つ。材料に入れないもの: 能動発信の投稿（`proactive` の
  印つき）、要約（role=summary）、委任の子（`delegate-*` の
  セッション）。材料が大きい場合は上限（12000 字）で切り、
  処理した分だけ位置を進める（1 件だけで上限を超える発話は
  切って取り込む）。
- **モデルの呼び方**: 道具なしの単発 chat で、新しい会話の
  抜粋と現在の MEMORY.md を渡し、「事実・好み・決めたこと・
  約束のうち残す価値があるものを、今の MEMORY.md の文体に
  合わせた箇条書きで。すでに書いてある内容は繰り返さない。
  無ければ『なし』」と指示する。モデルは巡回している
  セッションの頭脳（Web 巡回ならそのユーザーの Session の
  モデル）を使う。箇条書きでない応答・空の応答・例外は失敗
  として扱い、MEMORY.md は変更しない。
- **適用の作法**: 箇条書きが返れば、書き込む前に必ず
  `MEMORY.md.bak-<日時>` へ控えを取り（整理と同じ作法。
  MEMORY.md がまだ無い場合は控えは作らない）、末尾へ足して
  から機械的な重複除去を通す。足した結果が元の本文と変わら
  ない場合（すべて重複だった場合）は書き込まない。「なし」
  の場合も本文は変えない。成功・「なし」・変更なしの場合は
  処理済み位置を進め、失敗の場合は進めない（翌日に同じ分
  から再挑戦できる）。
- **入口は 2 つ**:
  - **自動抽出**: 能動発信の巡回（`proactive`）の中で
    **1 日 1 回まで**実行する。試行日はモデルを呼ぶ前に記録
    するため、失敗した日もその日は再試行しない。新しい材料
    が無い日は試行として記録しない。モデルなしの一時
    Session の巡回（CLI の `kuma-agent proactive`）では
    実行せず、試行の記録も残さない（定期ジョブと同じ
    ガード）。テナントの能動発信が OFF のときは巡回自体が
    無いため行わない。会話への投稿はしない。環境変数
    `KUMA_MEMORY_EXTRACT=0` で無効化できる。
  - **CLI `kuma-agent memory-extract`**（`--tenant` / `--user`
    で対象を指定）: 明示的な実行なので、無効化の環境変数や
    1 日 1 回の上限は適用しない（モデルが要るため API キー
    必須のコマンドとして配置する）。`--dry-run` では本体も
    状態も変更せず、提案される箇条書きだけを表示する。

## 会話の横断検索

過去の会話そのものを、セッションを越えて探す仕組み。長期記憶の
検索が「書き留めた事実」を探すのに対し、こちらは「実際に交わした
発言」を探す（`memory.search_conversation_records`）。

- **対象**: 現在のユーザーの置き場にある会話記録すべて
  （`conversations/*.jsonl`、全セッション。委任の子の記録
  `delegate-*` も含む）を、発話単位で検索する。テナントや
  ユーザーを越えては探さない（記録の置き場の区切りに従う）。
- **照合と並び順**: 長期記憶の検索と同じ流儀。クエリを空白・
  句読点で語に分け、各語の部分文字列一致で「一致した語の数」を
  主、「語の出現回数」を副として点数付けし、同点は新しい発話を
  優先する。新しさは記録の日時（`ts`）で判定し、日時が無い・
  解釈できない記録はファイルの更新時刻で代用する。壊れた行や
  読めないファイルは読み飛ばし、検索全体は落とさない。
- **ヒットの形**: 「（セッション名、日時、話者）本文の抜粋」の
  1 行。話者は利用者／クマ（要約発話は「要約」）と分かる表記に
  直す。日時の無い記録では日時の部分を省く。抜粋は改行を潰し、
  長い発話は一致箇所の前後 200 字程度に切り出す（切り捨てた
  側に「…」を付ける）。
- **入口**: 道具 `search_conversations`（引数は `query` と任意の
  `limit`、既定 5。0 件は「見つかりませんでした」。作業中表示は
  「過去の会話を検索中」）と、CLI `kuma-agent search-history
  <クエリ>`（`--tenant` / `--user` / `--limit` 指定可、API キー
  不要）。道具は会話記録の検索であり用事や長期記憶の仕組みとは
  独立なため、モードを問わず登録する（スレッドモードでも出す。
  長期記憶の検索道具が相棒モードだけなのと対照的）。
- **長期記憶の検索との違い**: 対象が MEMORY.md の項目ではなく
  会話記録の発話である点、出どころが「MEMORY.md の行番号」で
  はなくセッション名と日時である点が違う。長期記憶に残らな
  かった言い回しや、セッションをまたいだ経緯を探す用途に向く。

## 手順書（スキル）

特定の仕事の進め方を Markdown で書いた再利用可能な指示書
（`skills.py`）。人格や長期記憶とは別に、「やり方」だけを持ち回る。

- **置き場と形式**: データ置き場ルートの `skills/` に置き、
  **全テナント共通**とする（運用者が置く前提。テナントや
  ユーザーでは分けない）。1 件の置き方は 2 通りで、フォルダ形式
  `skills/<名前>/SKILL.md` と単一ファイル `skills/<名前>.md` の
  どちらでもよい。ファイルの先頭には簡易ヘッダー（`---` で
  囲んだ `name:` と `description:`）を置ける。YAML ライブラリは
  使わず行単位の単純な解析で読み、ヘッダーが無い・欠けている
  場合は名前をファイル/フォルダ名から、説明を本文の最初の
  見出しまたは先頭行から補う。読めない・壊れたファイルがあって
  も走査全体は落とさず読み飛ばす。
- **目次だけをプロンプトに入れる**: セッション開始時に走査し、
  システムプロンプトには「使える手順書」として名前と説明だけの
  目次を添える。本文まで載せると件数が増えるほど文脈を圧迫する
  ため、本文は必要なときに道具で読む。手順書が 1 件も無ければ
  目次自体を出さない。新しい手順書は次回セッションから反映
  される（常時監視はしない）。
- **道具**: `read_skill`（名前で本文を返す。無い名前は error）と
  `save_skill`（名前・説明・本文を受けてフォルダ形式で保存、
  同名は上書き）。`save_skill` があることで、会話の中で利用者
  から手順を教わって手順書として覚える、という使い方ができる。
  名前はパスに使える安全な文字列だけを許可する（英数・
  ハイフン・アンダースコア・日本語可、区切り文字と `..` は
  不可）。道具が出る範囲は用事系の道具と同じ（相棒モードで、
  API 系の頭脳の道具ループに載る）。作業中表示は `read_skill`
  が「手順書を読んでいます」、`save_skill` が「手順書を書き
  留め中」。
- **注意**: 手順書の本文はモデルの指示として実行される。出所の
  分からない手順書を置かないこと（MCP サーバーと同じく、置ける
  のは運用者だけという前提に立つ）。

## 委任（別のエージェントへ仕事を渡す）

独立して進められる仕事を、子エージェントに丸ごと渡す仕組み
（`delegate.py`、道具 `delegate`）。

- **子の構成**: 子は新しい Session として作る。人格・長期記憶・
  テナント・ユーザーは親と同じで、頭脳は親と同じプロバイダ。
  モデルは環境変数 `KUMA_DELEGATE_MODEL` があればそれ、無ければ
  親と同じモデル。道具はファイル・用事・記憶・MCP・手順書など
  親と同じ構成を使う。システムプロンプトには「委ねられた仕事の
  担当であること、最後の応答が依頼元への報告になること」を
  一文足す。
- **委任は1段まで**: 子には `delegate` 道具を登録しない。孫まで
  広げると仕事の範囲と費用が際限なく膨らむため、深さは 1 で
  切る。
- **会話と記録**: 子の会話は親と混ぜない。セッション ID は
  `delegate-<日時>-<連番>` で、会話記録は通常どおり
  `conversations/` に残るため、後から何を頼んで何が起きたかを
  辿れる（相棒モードでも部屋の固定＝main の対象にしない）。
- **実行の形**: 同期実行。親の道具呼び出しの中で子へ依頼文を
  1 発話として渡し、子の最終応答を道具の結果として親へ返す。
  子の作業中表示は「別のエージェントが作業中（…）」として親の
  表示へ中継する。制限時間は環境変数
  `KUMA_DELEGATE_TIMEOUT_SECONDS`（既定 600 秒）。子の実行は
  別スレッドで行い、時間切れや子の例外は例外ではなく `error:`
  の道具結果として親へ返し、親の会話は続ける。道具ループの
  回数上限は親と同じ（同じ Config の `max_tool_rounds`）。
- **承認の継承**: 子の道具実行でも親と同じ承認の仕組みが働く
  （親の承認者をそのまま子へ配線する）。承認者が付いていない
  経路では通常の道具と同じく安全側に倒す（対象道具は却下）。

## Web 道具（検索とページ取得）

外部の情報を調べるための組み込み道具（`webtools.py`、道具
`web_search` / `fetch_page`）。基本道具の仲間として、モードを
問わず道具ループが回る経路（API 系の頭脳）で出す。取得は
httpx（既存依存のみ）、抽出は標準ライブラリの html.parser で
行う。

- **検索（web_search）**: 検索エンジンはキー不要の DuckDuckGo
  HTML 版（`https://html.duckduckgo.com/html/?q=...`）。結果の
  HTML からタイトル・URL・要約を抽出し、一覧の文字列で返す。
  結果リンクは DuckDuckGo のリダイレクト形式
  （`uddg` パラメータ）で来るため、実際の URL に戻してから
  返す。検索先は環境変数 `KUMA_SEARCH_URL`（`{query}` を含む
  テンプレート）で差し替えられる。返す件数は引数 `limit`
  （既定 5）。
- **ページ取得（fetch_page）**: http/https のみ。リダイレクト
  は最大 5 回まで追従する（通常のブラウザに近い User-Agent、
  タイムアウト 15 秒）。HTML は script/style 等を取り除いて
  本文テキストを抽出し、見出しや段落の区切りは改行で残す。
  プレーンテキストの応答はそのまま使う。返す本文は最大
  8000 文字で切り、切った場合はその旨を末尾に付ける。取得
  失敗や非対応の形式は例外ではなく `error:` の結果にする。
- **SSRF 対策**: 既定では localhost とプライベート IP 宛先へ
  の取得を拒否する。判定はホスト名を解決した後の IP
  （IP リテラルならそのもの）で行い、リダイレクトの飛び先も
  毎回確認する。許可するのは環境変数
  `KUMA_FETCH_ALLOW_PRIVATE=1` のときだけ（手元の開発用
  サーバーを読む場合など運用者の判断に限る）。
- **外部情報の扱い**: 検索結果も取得した本文も「資料」であって
  「指示」ではない。ページ中に指示のような文言が含まれて
  いても、それに従って行動しない（プロンプトインジェクション
  対策）。道具の説明文にもその旨を明記し、モデルには情報と
  してだけ使わせる。

## Telegram 接続

Telegram の Bot から会話できる接続（`telegram.py`）。Bot API を
httpx で叩き、`getUpdates` のロングポーリングでメッセージを受け、
応答を `sendMessage` で返す。Bot API の呼び出しは差し替え可能な
形（`TelegramApi`）にしてあり、テストはネットワークに出ない。

- **設定（環境変数）**:
  - `KUMA_TELEGRAM_BOT_TOKEN`: Bot トークン。Bot は Telegram の
    @BotFather で作成し、発行されたトークンをこの変数に設定する。
    未設定なら Telegram 機能は無効（Web / CLI の通常動作には影響
    しない）。トークンはリクエスト URL に含まれるため、ログや
    例外の文面には出さない。
  - `KUMA_TELEGRAM_TENANT`（既定 `default`）と
    `KUMA_TELEGRAM_USER`（既定 `default`）: 届いたメッセージを
    処理するテナントとユーザー。CLI / Web の起動時指定とは別の、
    Telegram 経路専用の行き先である。
  - `KUMA_TELEGRAM_ALLOWED_CHATS`: 会話を許可する chat id の
    カンマ区切り。
  - `KUMA_TELEGRAM_PROACTIVE`（既定は有効、`0` で無効化）:
    能動発信の Telegram 配信の ON/OFF（次項）。
- **許可リストの意味**: 未設定・空のときは会話を処理しない。届いた
  メッセージには「このチャットはまだ登録されていません。chat id は
  XXX です」という趣旨の案内だけを返し、運用者がその id を知って
  許可リストへ設定できるようにする。許可された chat id 以外からの
  メッセージも同様に案内だけを返す（会話の内容はモデルへ渡らない）。
- **会話の行き先**: 相棒モードではそのユーザーの `main` の会話で、
  Web UI と履歴（記録ファイル）を共有する。スレッドモードでは
  `telegram-<chat id>` という名前の会話になる。返信は Telegram の
  上限（4096 字）に合わせて分割して送る（なるべく改行で切る）。
- **能動発信の配信**: 巡回が main の会話へ投稿する内容（日報・
  時刻指定リマインダー・定期ジョブの結果と失敗の知らせ）は、
  Telegram にも送られる（`telegram.build_proactive_notifier` が
  作る通知コールバックを、巡回が投稿のたびに呼ぶ）。
  - **届け先**: 対象は `KUMA_TELEGRAM_TENANT` /
    `KUMA_TELEGRAM_USER` が指すテナント／ユーザーへの投稿だけ
    で、他のテナント／ユーザーの投稿は送らない。送り先は許可
    リスト（`KUMA_TELEGRAM_ALLOWED_CHATS`）の全チャットで、
    文面は返信と同じく 4096 字に分割して送る。
  - **無効化と未設定**: `KUMA_TELEGRAM_PROACTIVE=0` で配信だけ
    を止められる（会話への投稿と Telegram での会話は従来どお
    り）。Bot トークン未設定・許可リスト空の場合は、どちらに
    せよ何も送らない。
  - **失敗時の扱い**: 送信に失敗しても会話への投稿は成立させる
    （通知側で例外を飲み、標準エラーへ短く出す）。再送・リトライ
    はしない（二重送信を避けるため）。
- **処理済み位置**: `update_id` のオフセットはデータ置き場ルートの
  `telegram_state.json`（`{"offset": <次の update_id>}`）に、更新を
  処理するたびに保存する。再起動しても処理済みの更新は再処理
  しない。
- **起動方法**: 2 つある。(1) `kuma-agent web` 起動時にトークンが
  設定されていれば、裏側スレッドでポーリングを始める（能動発信の
  巡回と同じ流儀）。(2) `kuma-agent telegram` で単独実行でき、
  Web UI なしでも動く（フォアグラウンド、Ctrl-C で終了。モデルの
  API キーは通常どおり必要）。ポーリングの失敗（通信エラー等）では
  スレッドを落とさず、少し待って再試行する。
- **承認の扱い**: Telegram 経路の Session には承認者を付けない。
  そのため承認が必要な道具（`run_shell` と MCP 道具）は既存の
  仕組みで安全側に倒れ、Telegram からの会話では常に却下される
  （Web UI の承認パネルには出ない）。承認が要る操作は Web UI 等の
  承認者がいる経路で行う。
- **添付は未対応（将来課題）**: テキスト以外のメッセージ（写真・
  ファイル等）には「今はテキストだけ対応しています」と返す。
  Telegram の添付を Session の添付として渡す対応は将来課題とする。

## LINE 接続

LINE の公式アカウントから会話できる接続（`line_api.py`）。Telegram
のロングポーリングと違い、LINE は **Webhook** 方式で、LINE の
サーバーが運用者の公開 HTTPS URL へイベントを POST してくる。
受け口は Web UI のサーバーが持つ `POST /line/webhook` で、送信は
Messaging API（`https://api.line.me/v2/bot/message/reply` と
`/push`、認証は `Authorization: Bearer <チャネルアクセストークン>`）
を httpx で叩く。送信 API の呼び出しは差し替え可能な形（`LineApi`）
にしてあり、テストはネットワークに出ない。

- **署名検証（守りの中核）**: ヘッダー `X-Line-Signature` は、
  リクエストボディに対する HMAC-SHA256（チャネルシークレット）を
  Base64 化したもの。検証は `hmac.compare_digest` で行い、合わない
  リクエストは 400 で断る。Webhook の URL は公開されるため、この
  検証が唯一の守りになる。
- **ログインゲートとの関係**: `/line/webhook` は Web UI の
  ログイン（`KUMA_WEB_PASSWORD`）の対象外にする。LINE のサーバー
  は Cookie を持たないためで、ログイン必須の設定でも Webhook は
  署名検証だけで通す。その他の経路は従来どおり守られる。
- **即時応答と裏側処理**: 署名が合えば即座に 200 を返し、会話の
  処理（モデルの呼び出しと返信）は裏側のスレッドで行う。モデルが
  遅くても LINE 側の Webhook を待たせない（タイムアウトによる
  再送を避ける）。
- **対象イベント**: 1 対 1（`source.type == "user"`）の message
  イベントだけを処理する。グループ・ルーム宛てのイベントと、
  follow 等の他種イベントは何もせず無視する（グループ対応は
  未対応）。
- **設定（環境変数）**:
  - `KUMA_LINE_CHANNEL_SECRET`: チャネルシークレット（署名検証用）。
  - `KUMA_LINE_CHANNEL_ACCESS_TOKEN`: チャネルアクセストークン
    （送信 API の認証用）。
  - この 2 つが両方そろったときだけ受け口が有効になる。片方でも
    未設定なら `/line/webhook` は 404 で、LINE 機能は無効（Web /
    CLI の通常動作には影響しない）。トークン・シークレットは
    ログや例外の文面には出さない。
  - `KUMA_LINE_TENANT`（既定 `default`）と `KUMA_LINE_USER`
    （既定 `default`）: 届いたメッセージを処理するテナントと
    ユーザー。LINE 経路専用の行き先である。
  - `KUMA_LINE_ALLOWED_USERS`: 会話を許可する user id のカンマ
    区切り。
  - `KUMA_LINE_PROACTIVE`（既定は有効、`0` で無効化）: 能動発信の
    LINE 配信の ON/OFF（後述）。
- **許可リストの意味**: 未設定・空のときは会話を処理しない。届いた
  メッセージには「このユーザーはまだ登録されていません。あなたの
  user id は XXX です」という趣旨の案内だけを返し、運用者がその
  id を知って許可リストへ設定できるようにする（Telegram の chat id
  案内と同じ流儀）。許可された user id 以外からのメッセージも
  同様に案内だけを返す（会話の内容はモデルへ渡らない）。
- **会話の行き先**: 相棒モードではそのユーザーの `main` の会話で、
  Web UI と履歴（記録ファイル）を共有する。スレッドモードでは
  `line-<user id>` という名前の会話になる。
- **返信の送り方**: まず Reply API（Webhook イベントの
  `replyToken` を使う。無料で月間の通数に数えない）で送る。
  replyToken の有効期間は短い（おおむね 1 分）ため、Reply が
  失敗したら Push API に切り替えて全通を送り直す。テキストは
  1 通 5000 字までなので、長い返信は 5000 字で分割する（なるべく
  改行で切る。分割は telegram のものを共用）。Reply は最大 5 通
  まで同時に送れるため、先頭の 5 通を Reply で送り、超える分は
  Push API で送る（Push も 1 回最大 5 通で分ける）。
- **能動発信の配信**: 巡回が main の会話へ投稿する内容（日報・
  時刻指定リマインダー・定期ジョブの結果と失敗の知らせ）は、
  LINE にも送られる（`line_api.build_proactive_notifier` が作る
  通知コールバックを、Telegram の分と `combine_notifiers` で
  まとめて巡回へ渡す）。
  - **届け先**: 対象は `KUMA_LINE_TENANT` / `KUMA_LINE_USER` が
    指すテナント／ユーザーへの投稿だけで、送り先は許可リスト
    （`KUMA_LINE_ALLOWED_USERS`）の全ユーザー。送信は Push API
    で、文面は 5000 字に分割して送る。
  - **通数の注意**: Push API の送信は月間の無料通数（プランごと
    の上限）に数える。日報などの能動発信も 1 投稿 = 届け先
    1 人につき 1 通以上を消費するため、通数を抑えたい場合は
    `KUMA_LINE_PROACTIVE=0` で配信だけを止められる（会話への
    投稿と LINE での会話は従来どおり）。Reply API の返信は
    通数に数えない。
  - **無効化と未設定**: チャネルアクセストークン未設定・許可
    リスト空の場合は、どちらにせよ何も送らない。
  - **失敗時の扱い**: Telegram の配信と同じく、送信に失敗しても
    会話への投稿は成立させる（通知側で例外を飲み、標準エラーへ
    短く出す）。再送・リトライはしない（二重送信を避けるため）。
- **承認の扱い**: LINE 経路の Session には承認者を付けない。
  そのため承認が必要な道具（`run_shell` と MCP 道具）は既存の
  仕組みで安全側に倒れ、LINE からの会話では常に却下される
  （Telegram と同じ）。
- **添付は未対応**: テキスト以外のメッセージ（画像・音声・
  スタンプ等）には「今はテキストだけ対応しています」と返す。
- **運用者側の準備手順**:
  1. LINE Developers コンソールでプロバイダーを作り、Messaging
     API チャネルを作成する。チャネル基本設定にある「チャネル
     シークレット」と、Messaging API 設定で発行する「チャネル
     アクセストークン（長期）」を控える。
  2. kuma-agent 側に `KUMA_LINE_CHANNEL_SECRET` と
     `KUMA_LINE_CHANNEL_ACCESS_TOKEN` を設定して Web UI を起動
     する（公開 HTTPS で到達できる必要がある。コンテナで公開
     する場合は前段のリバースプロキシ等で HTTPS 化する）。
  3. チャネルの Messaging API 設定で、Webhook URL に
     `https://<公開ホスト>/line/webhook` を登録し、検証が通る
     ことを確認する。
  4. LINE Official Account Manager 側で「Webhook」を有効化し、
     あいさつメッセージや応答メッセージ等の自動応答は切って
     おく（自動応答が残っていると、Bot の返信と二重に届く）。
  5. 公式アカウントを友だち追加して話しかける。最初は許可
     リストが空のため user id の案内が返るので、その id を
     `KUMA_LINE_ALLOWED_USERS` に設定して再起動すると会話が
     始まる。

## 音声（添付・録音・読み上げ）

音声の入出力は、既存の添付の仕組みとブラウザの機能に乗せる。
サーバー側に音声合成の処理は持たず、音声認識は文字起こしとして
Gemini に任せる（下記の「音声の文字起こし」）。

- **音声添付**: 添付の対応形式に音声（mp3 / wav / m4a / ogg /
  webm）を追加した。1 件の上限は他の添付と同じ 10MB。形式の
  判定は `llm.Attachment.is_audio`（メディア種別が `audio/*`、
  またはブラウザの録音が名乗る `video/webm`）。拡張子からの
  推定（`guess_media_type`）では webm を `audio/webm`、wav を
  `audio/wav`、m4a を `audio/mp4` にそろえる。Web の添付として
  受ける際、メディア種別に付いたパラメータ（`;codecs=opus`
  など）は落としてから扱う。TUI の `/attach` でも音声ファイル
  をそのまま指定できる（追加の UI は作らない）。
- **頭脳ごとの渡し方**（既存の添付の流儀に合わせる）:
  - **Gemini API**: 音声データをそのまま inline data
    （`audio/*` の MIME）で渡す。モデル側で内容を聞き取れる。
  - **Claude API / Muse API**: 音声を直接扱えないため、PDF の
    Muse 扱いと同じく「音声が添付されていたこと」の注記
    （プレースホルダ文）を渡し、データ自体は渡さない。
    文字起こしがあれば、その文章も注記に添えて渡す（下記）。
  - **CLI 系**: 既存の経路どおり、作業ディレクトリ配下の
    `.kuma-attachments/` にファイルとして置いて読ませる。
    文字起こしがあれば、その文章も指示に含める（下記）。
- **音声の文字起こし**: 今の頭脳が Gemini でない場合、Gemini の
  キー（GEMINI_API_KEY / GOOGLE_API_KEY）があれば、音声添付を
  頭脳へ渡す前に Gemini で文字起こしする（`transcribe.py`、
  Session が発話の合流点で行う）。使うモデルは Gemini の会話用
  既定モデルで、`KUMA_TRANSCRIBE_MODEL` で差し替えられる
  （画像生成用の `KUMA_IMAGE_MODEL` とは別）。文字起こしの
  文章は `Attachment.transcript` に載り、Claude / Muse では
  注記に「（文字起こし）…」として添え、CLI 系ではファイルの
  案内に添えて渡す。Gemini 頭脳のときは音声データ自体を渡す
  ため文字起こしはしない。キーが無い・文字起こしに失敗した
  場合は従来の扱い（注記のみ・ファイルのみ）に静かに戻り、
  会話は壊れない。環境変数 `KUMA_TRANSCRIBE=0` で無効化できる。
- **会話ログ**: 既存どおり添付の要約だけが残り、バイト列は
  残らない。音声の要約文は「[添付: 音声 <ファイル名>
  （<メディア種別>）]」の形で、音声であることが分かるようにする。
  文字起こしした場合は、その文章も要約に含めて残す。
- **Web UI の録音**: 入力欄の「録音」ボタンでブラウザの
  MediaRecorder を使い、マイクから録音する。録音中はボタンと
  状態表示で分かるようにし、停止すると音声ファイル
  （`recording-<時刻>.<拡張子>`、拡張子は録音形式から決める）
  として通常の添付フローに合流し、そのまま送信できる。
  マイクの許可が得られない場合やブラウザが未対応の場合は
  状態表示にエラーを出し、会話は壊さない。
- **Web UI の読み上げ**: アシスタントの発話ごとの「読み上げ」
  ボタンで、ブラウザの speechSynthesis（ja-JP）を使って
  その場で読み上げる。読み上げ中にもう一度押すか別の発話の
  ボタンを押すと止まる（別の発話は止めてからそちらを読む）。
  録音・読み上げはいずれもブラウザの機能であり、サーバー側の
  処理は追加しない。対応はブラウザとその音声環境に依存する。

## 成果物

エージェントが作ったファイルを、利用者が開ける形で渡す仕組み
（`outputs.py`、道具 `deliver_file`）。作業ディレクトリにファイルを
書くだけでは、サービスとして動かした場合に利用者の手元へ届かない
ため、成果物として登録されたファイルだけを Web 画面から取り出せる
ようにする。

- **置き場と index**: 成果物はユーザーごとの置き場に `outputs/`
  フォルダを作って置く。一覧は `outputs/index.json` に保持し、
  1 件の項目はファイル名（`filename`）、タイトル（`title`、画面に
  出す表示名）、サイズ（`size`、バイト数）、登録日時
  （`created_at`、ISO 8601）。読み書きは定期ジョブ（JobBoard）と
  同じ流儀で、書き込みの前に読み直し、ファイルが無い・壊れている
  場合は空の一覧として動き、壊れたレコードは読み飛ばす
  （`OutputBoard`）。
- **道具 `deliver_file`**: モードを問わず登録する（定期ジョブの
  道具と同じ配線）。引数は `path`（作ったファイルのパス）と任意の
  `title`（表示名。無ければファイル名）。実在する通常ファイルだけを
  受け、ディレクトリや存在しないパスは `error:` で返す。受けた
  ファイルは `outputs/` へコピーし、同名があれば拡張子の前に連番を
  付けて衝突を避ける（`report.txt` → `report-2.txt`）。戻り値は
  「成果物として登録しました。Web画面の「成果物」から開けます」
  の趣旨で、利用者がどこで開けるか分かる文面にする。作業中表示は
  「成果物を用意しています」。
- **Web の口**: ヘッダーの「成果物」ボタンでパネルを開く（テナント
  管理パネルと同じ流儀）。パネルは現在のテナント×ユーザーの成果物を
  タイトル・ファイル名・サイズ・日時の表で出し、各行にダウンロード
  のリンクを付ける。成果物が無い場合はその旨を表示する。パネルは
  開くたびに一覧を取り直す。API は `GET /api/outputs`
  （`tenant` / `user` を受け、一覧を JSON で返す）と
  `GET /api/outputs/download?name=<ファイル名>`（ファイル本体を
  `Content-Disposition: attachment` で返す）。ダウンロードで
  許可するのは index にあるファイル名だけで、basename の検証と
  実在確認でパストラバーサルはできない作りにする。
- **CLI**: 運用者は `kuma-agent outputs`（`--tenant` / `--user`
  で対象を指定、API キー不要）で一覧を確認できる。
- **クリーンアップ対象外（当面の判断）**: 成果物は保持期限の自動
  クリーンアップの対象に**含めない**。成果物はエージェントの内部
  記録ではなく「利用者に渡したもの」であり、渡した側が期限で勝手に
  消すと、利用者が後から開けなくなる。置き場が膨らむ懸念はあるが、
  消す判断は当面、利用者・運用者に委ねる（将来、成果物専用の保持
  期間を設ける場合はこの節を改める）。

## 画像生成

画像を作って利用者に渡す道具（`imagegen.py`、道具
`generate_image`）。成果物の置き場を使うため、成果物の道具と
同じ配線で、モードを問わず登録する（Session は常に成果物の
置き場を渡す）。作業中表示は「画像を作っています」。

- **生成だけ Gemini を使う**: 生成そのものは Gemini API の
  generateContent（画像生成対応モデル）に任せる。画像生成の口は
  手元の API では Gemini にしか無く、頭脳の選択と切り離して
  おくことで、今の頭脳が Gemini でなくても（CLI 系の頭脳でも）
  Gemini のキー（`GEMINI_API_KEY` / `GOOGLE_API_KEY`）さえ
  あれば生成できる。通信の作りは既存の Gemini クライアントと
  そろえ（同じベース URL・キー用ヘッダー・httpx）、新しい通信
  経路は作らない。使うモデルは環境変数 `KUMA_IMAGE_MODEL`
  （既定 `gemini-3.8-flash-image`）で差し替えられる。
- **成果物経由で渡す**: 応答の parts に含まれる画像データ
  （inlineData、base64）をファイルにし、成果物として登録して
  渡す。拡張子は mime に合わせ（png / jpeg / webp / gif、それ
  以外は png に倒す）、ファイル名は `image-<日時>` の形にする。
  道具の戻り値にはファイル名と「Web画面の「成果物」から開ける」
  旨を含める。会話の記録には道具の結果（テキストの要約）だけが
  残り、画像そのものは記録に埋め込まない。
- **対応しない場合はエラー**: キーが無い・通信に失敗した・
  応答に画像が含まれない場合は、例外ではなく `error:` の結果
  として返し、会話は壊さない。画像が無い場合、モデルの
  テキスト応答があれば短く添える。

## アクセス制御（ログイン）

Web UI をパスワードで守る仕組み（`web.py` の `AuthGate`）。画面を
自宅の外からも開けるようにする場合の、最低限の入口の守りである。

- **有効化の条件**: 運用者が環境変数 `KUMA_WEB_PASSWORD`
  （`Config.web_password`）を設定したときだけ有効になる。未設定
  なら従来どおり認証なしで全て開く（ローカル利用の既定は変え
  ない）。未設定＝認証なしの前提は従来どおりで、外に開ける場合
  はパスワードを設定するか、認証付きの逆プロキシを前に置く。
- **未ログイン時の振る舞い**: 画面（`/`）はログイン画面
  （`GET /login`）へリダイレクトし、API（`/api/...`）は 401 を
  返す。成果物のダウンロードを含む全経路が対象で、例外はない。
  ログイン画面はアバターとブランド色に合わせた、パスワード入力
  と送信ボタンだけの専用ページ。
- **ログインとトークン**: `POST /login` でパスワードを照合する
  （比較は `hmac.compare_digest`）。合えば `secrets` で推測でき
  ないトークンを発行し、Cookie（名前は `kuma_session`、HttpOnly、
  SameSite=Lax、Path=/、有効期間は30日）に入れる。トークンは
  サーバー側ではメモリ上にだけ保持するので、サーバーを再起動
  したら全員が再ログインになる（永続化はしない）。
- **ログアウト**: `POST /api/logout` でトークンを破棄し、
  Cookie を消す。ヘッダーの「ログアウト」ボタンは、ログインが
  有効なときだけ出す（未設定時は従来の見た目のまま）。
- **連続失敗の制限**: 同一 IP からパスワードを5回続けて間違える
  と、その IP からのログインを60秒間受け付けない（その間は
  正しいパスワードでも通さない）。記録はメモリ上だけの簡易な
  もので、再起動で消える。
- **Secure 属性**: Cookie の Secure 属性は既定では付けない
  （HTTP のローカル利用で Cookie が送られなくなるため）。HTTPS
  で公開する場合は、運用者が環境変数 `KUMA_WEB_SECURE_COOKIE=1`
  を設定すると付く。
- **対象外**: Telegram や能動発信などサーバー内部の動きには
  影響しない。CLI / TUI にもログインは無い（端末の前にいる人
  のものとして扱う）。また、ここでのログインは画面全体への
  入口の守りであり、テナント・ユーザーの識別（宣言による
  分離）とは別物である。

## 人格・記憶の編集

Web UI のヘッダー「人格・記憶」ボタンから開く編集パネルと、その
読み書きを担う `profile_files.py`。利用者が人格ファイルと長期
記憶を、ファイル置き場を直接触らずに画面から直せるようにする。

- **対象ファイル**: そのテナント×ユーザーの置き場にある 4
  ファイルだけ: 人格ファイルの SOUL.md（性格）/ IDENTITY.md
  （自己紹介）/ USER.md（利用者について）と、長期記憶の
  MEMORY.md。API（`GET` / `POST /api/profile`）は名前をこの
  ホワイトリストと完全一致で照合し、それ以外の名前は 400 で
  拒否する（パス区切りや .. を含む名前も同じく拒否される）。
  ファイルが無い場合は空として開き、保存で作られる。
- **ユーザーごとの分離**: 対象の置き場は他の API と同じ方法
  （tenant / user の指定と正規化）で解決する。別のユーザーの
  ファイルを読むことも書くこともできない。
- **保存の安全性**: 保存前に既存の内容を「ファイル名
  .bak-<日時>」へ控えとして残す（長期記憶の整理と同じ形式）。
  書き換え自体は一時ファイルへ書いてから `os.replace` で置き
  換える原子的な方法で行い、途中で止まっても元のファイルが
  壊れた状態にはならない。本文のサイズ上限は 200KB（UTF-8
  換算）で、超過は 400 で拒否する。
- **反映タイミング（正直な挙動）**: 人格と長期記憶は Session
  の生成時に読み込まれる（`load_persona` と
  `Memory.load_long_term`）ため、保存した内容が効くのは、その
  後に新しく作られるセッション（新しい部屋・再接続で作られる
  会話）からである。すでに開いているセッションの人格・記憶は
  途中で変わらない。プロセスの再起動は不要だが、開いている
  会話に即時反映されるわけではない。パネルにもこの旨を案内
  文として出す。
- **認証との関係**: ログイン（アクセス制御）が有効なときは、
  この API も他の API と同じく認証の対象になる（未ログイン
  なら GET は 401、POST も 401）。編集できるのは入口を通った
  人だけだが、テナント・ユーザーの識別自体は従来どおり宣言
  であって認証ではない点は変わらない。
- **対象外**: TUI / CLI には編集画面は無い（端末からは
  ファイルを直接編集する従来の方法を使う）。

## 使用量の記録と表示

頭脳（LLM）をどれだけ使ったかを記録し、利用者と運用者が見られる
ようにする仕組み。記録と集計は `usage.py`、表示は Web UI の
「使用量」パネルと CLI の `kuma-agent usage` が担う。

- **記録の単位と置き場**: モデルが応答するたびに、そのユーザーの
  置き場の `usage.jsonl` へ 1 行追記する（`Session._call_model`
  が呼び出しごとに記録する）。道具の往復で複数回モデルを呼ぶ
  場合は呼び出しごとに 1 行になる。委任の子セッションの呼び出し
  も、子の Session が同じユーザーの置き場へ記録するため、同じ
  ユーザーに集まる（行の `session_id` で親子を区別できる）。
  会話の要約のための呼び出しも通常の呼び出しと同じく記録する。
  一方、長期記憶の整理が内部で直接モデルを呼ぶ分は Session を
  経由しないため記録の対象外である。
- **記録の項目**: `ts`（日時）、`provider`（頭脳）、`model`
  （モデル名）、`input_tokens` / `output_tokens` / `total_tokens`、
  `session_id`。
- **頭脳ごとの使用量の出どころ**: API 系の頭脳は応答に使用量を
  含むため、各クライアントが形式の違いを吸収して正規化する
  （Muse は OpenAI 互換の `usage`、Claude は `usage` の
  input/output、Gemini は `usageMetadata`）。合計だけが無く入力
  と出力がそろっている場合は、合計をその和で補う。応答に使用量
  が無い・形式が想定外でも会話は壊さず、その項目は記録しない
  （None）。CLI 系の頭脳は使用量が取れないため、トークン数は
  すべて None で、呼び出し回数だけを記録する。
- **記録の失敗**: 記録は会話のついでに行うもので、書き込みに
  失敗しても会話自体は落とさない（例外は記録側で握りつぶす）。
- **集計と表示**: 集計は合計（呼び出し回数・入力・出力・合計
  トークン）と頭脳／モデル別、日別（直近30日、記録のある日だけ）
  の 3 種類。Web UI はヘッダーの「使用量」ボタンでパネルを開き
  （API は `GET /api/usage`、対象は他の API と同じ tenant / user
  の解決）、CLI は `kuma-agent usage`（`--tenant` / `--user`
  対応）で同じ内容をテキスト表示する。トークン数が記録されて
  いない区分（CLI 系の頭脳など）は、数値の代わりに記録が無い
  旨を表示する。
- **費用の換算はしない**: トークン数から費用は見積もらない。
  単価は頭脳・モデルごとに異なり、契約形態（従量・定額・CLI の
  ログイン利用）でも変わるため、ここでは使用量そのものだけを
  正直に見せる。
- **保持期限の対象外**: `usage.jsonl` は運用の記録として残す
  ため、保持期限の掃除（`cleanup_expired`）の対象にはしない
  （掃除の対象は部屋の記録と完了した用事だけ、という従来の
  範囲を変えない）。

## データの書き出し

ユーザーのデータをバックアップとして持ち出すための仕組み。
組み立ては `export.py`、入口は Web UI の「書き出し」ボタン
（`GET /api/export`）と CLI の `kuma-agent export`。

- **対象**: tenant / user で指した組み合わせのユーザー置き場に
  ある全データ（長期記憶・人格ファイル・会話記録・用事・成果物・
  使用量の記録など）。ただし、既定ユーザーの置き場はテナントの
  置き場そのもので、その配下の `users/` は他のユーザーの置き場
  であり、既定テナントでは配下の `tenants/` も他のテナントの
  置き場である。これらは対象ユーザーのデータではないため
  含めない。
- **形式**: ZIP。先頭に `export-info.json`（書き出し日時・
  テナント・ユーザー・kuma-agent の版・このファイルが書き出し
  である旨）を入れ、残りは置き場のファイルを相対パスのまま
  収める。置き場が無い・空でも、export-info.json だけの ZIP が
  できる。ファイル名の既定は
  `kuma-export-<テナント>-<ユーザー>-<日付>.zip`。
- **サーバーに残さない**: Web ではメモリ上で組み立てて
  ダウンロード応答として返し、サーバー側に書き出しファイルは
  作らない。ログイン有効時は他の API と同様に認証の対象になる。

## データの復元

書き出した ZIP を読み込んで、ユーザーのデータを戻すための
仕組み。組み立ては `restore.py`、入口は Web UI の「復元」
ボタン（`POST /api/import`）と CLI の `kuma-agent import`。

- **置き換え方式**: 対象ユーザーの置き場を、ZIP の内容で
  丸ごと置き換える。ZIP に無いファイルは消え、あるファイルは
  ZIP 側の内容になる。部分的なマージはしない。
- **復元前の自動控え**: 対象の置き場にデータがあれば、置き
  換えの前に現在の内容をユーザー単位の書き出し ZIP として
  データ置き場ルートの `backups/` へ保存する（ファイル名は
  `user-<テナント>-<ユーザー>-<日時>.zip`）。控えが作れなけ
  れば復元は中止する。
- **検証**: 先頭の `export-info.json` の format が
  "kuma-agent export" であることを確かめる。ZIP の項目は
  書き出す前にすべて検証し、絶対パスや `..` を含む項目、
  シンボリックリンクの項目があれば何も変更せずに中止する。
  サイズ上限は 100 MB。テナント削除前の控え ZIP（format が
  "kuma-agent tenant backup"）は復元元には使わない。
- **除外の鏡像**: 書き出しと同じ分離ルールを鏡像で守る。
  既定ユーザーの置き場配下の `users/`、データ置き場そのもの
  が置き場になる場合の `tenants/` にあたる項目は書き込まず、
  置き換えの際もその配下は消さない。データ置き場そのものが
  対象のときは、サーバーの控え置き場 `backups/` も消さない。
- **対象の決め方**: 既定は ZIP の `export-info.json` に記録
  されたテナント／ユーザー。CLI の `--tenant` / `--user` や
  Web のクエリで別の組み合わせにも復元できる。
- **Web の反映**: 復元に成功したら、対象ユーザーの開いて
  いる会話（Session）は破棄され、次に開く会話から復元後の
  データで始まる。ログイン有効時は他の API と同様に認証の
  対象になる。

## コンテナで動かす

サービスとして常駐させるためのコンテナ一式（`Dockerfile` /
`docker-compose.yml` / `.env.example` / `.dockerignore`）。

- **構成**: `Dockerfile` は `python:3.12-slim` を土台に、実行に
  必要なファイル（`pyproject.toml`、`README.md`、`src/`、
  `assets/`）だけをコピーして `pip install .` で導入する。
  実行は root 以外の専用ユーザー。`docker compose up -d --build`
  で起動し、`http://localhost:8765` で Web UI を開く。生存確認
  （HEALTHCHECK）は slim に curl が無いため、Python 標準の
  urllib でトップページを確認する。
- **MCP サーバーの同梱（0.39.0 から）**: ブラウザ操作と
  Google カレンダーの MCP サーバーをコンテナでも使えるよう、
  Node.js（公式 `node:22-slim` イメージから `/usr/local` を
  コピー）と Chromium（apt の `chromium`、日本語表示のため
  `fonts-noto-cjk` も）を入れ、2 つの MCP サーバー
  （`@playwright/mcp` / `@cocal/google-calendar-mcp`）を
  グローバル導入してある。そのためコンテナでは npx の初回
  取得を待たず、コマンド名（`playwright-mcp` /
  `google-calendar-mcp`）で直接起動できる。Playwright MCP
  には同梱ブラウザでなくシステムの Chromium を
  `--executable-path /usr/bin/chromium` で使わせる（設定例は
  「ブラウザ操作」「実サービスの接続例」の各小節）。Node.js
  と Chromium の分、イメージは大きくなる。
- **HOME と認証の永続化**: コンテナの `HOME` は `/data/home`
  にしてある。これにより Google カレンダーのトークン
  （`~/.config/google-calendar-mcp/tokens.json`）のような
  ホーム配下の状態もデータボリュームに残り、コンテナを
  作り直しても消えない。`GOOGLE_OAUTH_CREDENTIALS` は
  `/data` に置いたファイル（例 `/data/gcp-oauth.keys.json`）
  を指す。認証まわりの手順は「実サービスの接続例」の小節を
  参照。なおカレンダーの認証情報はボリュームに置かれる
  ため、ボリューム自体を秘密情報として扱うこと。
- **データはボリュームに置く**: データ置き場は `KUMA_DATA_DIR=/data`
  とし、compose の名前付きボリュームを `/data` に割り当てる。
  会話・長期記憶・用事・成果物などの状態はすべてここに集まる
  ので、イメージを作り直したりコンテナを差し替えたりしても
  データは残る（保持期限の掃除も、従来どおりこの中の記録が対象）。
- **キーは環境変数からだけ**: API キーや Bot トークンは compose の
  `env_file`（`.env`）経由で渡す。`.env` は `.dockerignore` で
  除外し、イメージに秘密を含めない。見本は `.env.example`
  （実値は空）。
- **API キーが無いと起動時に終了する**: `kuma-agent web` は起動前に
  頭脳の API キーを確認し、未設定なら終了する（従来の CLI と同じ
  動作）。キーを書き忘れたまま compose で起動すると、再起動を
  繰り返すので、まず `.env` を確認すること。
- **CLI 系の頭脳はコンテナでは使えない**: `claude-code` /
  `gemini-cli` / `codex` はコンテナ内に各 CLI 本体が無く、ログイン
  もできないため使えない。コンテナでは API 系（`muse` /
  `claude` / `gemini`）から選ぶ。
- **待ち受けと認証なしの注意**: コンテナ外から届くよう `--host
  0.0.0.0` で待ち受ける。Web UI は認証を持たない単一ユーザー前提
  なので、ポートを外のネットワークへ開ける場合は、認証付きの
  逆プロキシを前に置くなど運用者側で守ること（compose ファイルの
  コメントにも明記）。
- **アバターの置き場所**: pip 導入した環境ではリポジトリ配置に
  `assets/` が無いため、`load_avatar_svg` はカレントディレクトリの
  `assets/avatar.svg` も候補にして探す。Docker では `WORKDIR`
  （`/app`）に `assets/` をコピーしてあるので、そのまま表示できる。
  どちらにも無ければ従来どおり簡易表示になる。

## 安全装置

- 取り返しのつかない操作（削除、送信、公開）は利用者の確認を取る
  （道具の実行前確認は「承認（危険な操作の確認）」節）
- API キーは環境変数からのみ読む（`META_MODEL_API_KEY`）
- 道具の実行範囲は作業ディレクトリと許可リストに制限する

## LLM バックエンド（決定済み）

頭脳は差し替え可能にし、5 種を用意する。選択は環境変数
`KUMA_LLM_PROVIDER`（既定 muse）、モデルは `KUMA_LLM_MODEL`。

API 系（kuma-agent が道具ループを回す）:
- `muse`: Meta Model API（Muse Wonder）。キー: META_MODEL_API_KEY
- `claude`: Anthropic Messages API。キー: ANTHROPIC_API_KEY
- `gemini`: Google Gemini API。キー: GEMINI_API_KEY

CLI 系（相手側が道具ループを持つ。文脈をプロンプトで渡し、作業
ディレクトリでヘッドレス実行する。認証は各 CLI のログインを使う）:
- `claude-code`: Claude Code CLI（`claude -p`）
- `gemini-cli`: Gemini CLI（`gemini -p`）
- `codex`: OpenAI Codex CLI（`codex exec`、workspace-write サンドボックス）

既定モデルは 2026-11 時点の最新に合わせている（Claude Sonnet 5.5 /
Opus 5.5、Gemini 3.8 Flash / 4 Argon）。モデルは移り変わりが速いので、
既定値は定期的に見直す前提で各クライアントに明記する。

## Meta Model API の使い方

- OpenAI 互換の Chat Completions 形式（`https://api.meta.ai/v1`、
  モデル `muse-wonder-1.0`、Bearer 認証）
- 人格などの誘導は `developer` ロールで渡す
- 関数ツールは OpenAI 形式。`stop`・`logit_bias`・
  `reasoning_effort="none"` は送らない（400 になる）
