# VERIFY.md（push 前の検証チェックリスト）

kuma-agent は PR・CI の関門が無く main へ直接 push するため、`python -m pytest` のローカル全量が
唯一のテスト関門です。このファイルは「検証した」と言える条件を固定します。
画面資産や実動記録は装飾ではなく、実際に動かしたことの証拠（E2E の証拠）として扱います。

## すべての push で行うこと

1. `python -m pytest` を全量実行し、通過を確認する（省略しない）。
   時間が問題になる場合は「変更範囲 → 全量」の2段に分けてもよいが、全量は push 直前に必ず1回回す。
2. 結果（件数と成否）を完了報告に残す。

## UI 変更時（Web UI / TUI の見た目・操作が変わる場合）

1. Web UI／TUI を実際に起動して実画面で確認する。
2. README の画面資産を撮り直して差し替えるまでを一区切りにする:
   - `assets/screenshot-web.png` / `assets/screenshot-tui.png`
   - `assets/demo-web.gif` / `assets/demo-tui.gif`（最後のコマは約5秒保持）
   - テーマ別（light/dark/system/pixel）×PC／スマホの静止画と、8ビットの動画
     `assets/demo-web-pixel-<pc|mobile>.gif`
3. 会話の中身だけスタブモデルの応答に差し替える（実データを画面資産に残さない）。

## 振る舞いに触れる変更時

- 対話・記憶・定期ジョブ等の振る舞いに触れる変更は、実際に1往復動かした記録
  （入力と応答の要約）を完了報告へ添える。テストの通過だけで「動いた」としない。

## 往復・同等性の検証（手書き）

- 開発専用のテスト依存（Hypothesis 等）は入れない方針（2026-11-21 所有者承認）。
- 往復変換（export→import で元に戻る等）や同等性の検証が要る場合は、標準の parametrize 等で
  境界値を手書きして代替する。

## Verified トレーラー

コミット末尾に、どう検証したかを `Verified:` トレーラーで記録する（未検証も記録する）。

| 値 | 意味 |
|---|---|
| `pytest-full` | pytest 全量を実行し通過した |
| `pytest-full+ui-assets` | pytest 全量に加え、UI の実画面確認と README 画面資産の撮り直しまで行った |
| `docs-only` | 文書だけの変更で、pytest 全量を実行し通過した（振る舞いの変更なし） |
| `none` | 検証していない（理由をコミットメッセージ本文に書く） |

## 直らないとき

- 同じテスト失敗の修正が3ラウンド続いたら、粘らず止めて人間に上げる
  （`AGENTS.md` の「push 前レビューと検証」節）。
